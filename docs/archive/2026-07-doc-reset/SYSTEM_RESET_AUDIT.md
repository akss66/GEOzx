# DyFlow 系统重整审查

> 日期：2026-07-02
> 结论：当前系统不是“完全没做”，而是“核心闭环有雏形，但范围过宽、示例能力过多、真实能力与占位能力混在一起”。下一步应先收敛产品，而不是继续堆后端细节。

## 一、当前真实状态

### 已经成立的核心骨架

- 登录、应用外壳、路由保护、管理员路由已经存在。
- 运营大脑首页已经具备主流程雏形：输入目标 -> 选择项目/账号/平台 -> 生成 Brief -> 确认执行 -> 查看任务队列、风险、Trace。
- 后端已经有真实 FastAPI 路由、数据库模型、迁移和测试，覆盖认证、账号矩阵、运营大脑、专家团、任务编排、交付物验收、复盘指标、优化建议、成本、风险队列。
- 复盘建议可以送入运营大脑，形成下一轮 Brief，这是系统闭环里最有价值的方向之一。
- 任务/验收页保留了六阶段内容流水线，可作为默认参考链路。

### 还没有达到产品可信度的地方

- 导航展示了一个完整企业平台，但客服、投流仍是占位页；复盘看板部分图表仍是示例数据。
- 投流已决定暂缓，但侧边栏仍暴露“投流”，页面还写着千川、自动投放、ROI、大额投放，承诺超过当前范围。
- 专家团 API 有真实接口，但“当前任务”“直接调用结果”仍偏模拟，用户会感觉它不是从真实调度状态里长出来的。
- `tasks/plan.md` 仍把 B4 rerun_scope 当第一优先级，和当前“系统重整审查”的真实需要不一致。
- 前端页面数量多，但第一条主路径还不够像一个完整产品：任务从生成到验收、返工、复盘、再生成下一轮任务的叙事没有集中呈现。

## 二、系统不满意的根因

1. **产品范围过大**：8 个 Agent、投流、客服、复盘、成本、风险、知识库、账号矩阵全部同时出现，用户看到的是平台蓝图，不是可用产品。
2. **核心路径被稀释**：真正应该突出的 MVP 是“运营目标 -> Brief -> 专家调度 -> 交付物验收 -> 复盘建议 -> 下一轮任务”，但导航和页面把注意力分散到多个半成品模块。
3. **真实能力和演示能力混杂**：有些模块是真 API，有些是 mock/示例数据，有些是占位页，但 UI 语气没有足够明确地区分。
4. **计划文件过度偏工程任务**：当前计划继续追 B4/F5/Postgres 验证，会让产品继续变厚，但不会先解决“系统不好用、不可信、不收敛”的核心问题。

## 三、重整后的 MVP

本轮只保留一条主线：

```text
输入运营目标
  -> 生成结构化 Brief
  -> 运营大脑拆解计划
  -> 调用专家团
  -> 生成交付物
  -> 分项验收 / 打回重跑
  -> 形成复盘建议
  -> 送回运营大脑生成下一轮任务
```

### MVP 内保留

- 运营大脑
- 专家团，但只作为“当前任务与能力说明”，不强调直接调用
- 任务/验收
- 账号矩阵，仅用于任务范围绑定
- 复盘看板，仅保留真实数据和优化建议闭环
- 风险队列 / 质量门
- 成本页，保留为运维视角
- 知识库，作为 Agent 上下文来源

### 本轮隐藏或降级

- 投流：从主导航隐藏；仅保留模型枚举、Agent 资料和后续排期。
- 客服：从主导航隐藏；保留为后续反馈数据源，不进入当前 demo 闭环。
- 复盘中的投流 ROI、评论情感、私域漏斗等示例图：隐藏或统一收进“待接入数据源”折叠区。
- 专家团直接调用：降级为管理员/调试入口，避免用户把它当主流程。

## 四、首要任务

首要任务不是 B4，也不是 Playwright，也不是 Postgres downgrade。

**首要任务是：做“产品收敛切片”。**

验收标准：

- 侧边栏只暴露当前 MVP 可完成的模块。
- 首页/运营大脑能清楚承载唯一主流程。
- 所有占位、示例、暂缓能力不再以正式功能入口出现。
- 复盘闭环只展示真实数据和可送回运营大脑的优化建议。
- 计划文件、TODO、SPEC 中的近期目标一致，不再一边说投流暂缓，一边让投流出现在主路径里。

## 五、建议执行顺序

> 2026-07-02 优先级再调整：用户确认抖音 / 小红书 / 视频号接入重要性高于继续打磨纯内部编排。因此在运营大脑 UI 重排前，先做“平台接入底座”，让系统真正连接外部运营账号。

1. **S1 导航与范围收敛**：隐藏投流、客服，压缩主导航，明确“当前可用”和“后续能力”边界。
2. **P0 平台接入底座**：统一抖音 / 小红书 / 视频号的账号授权状态、外部账号 ID、接入状态、数据同步状态和回流入口。
3. **P1 抖音优先接入**：优先打通账号授权/识别、基础数据回流入口；发布动作先走可审计的半自动记录，真实发布按权限推进。
4. **P2 小红书、视频号接入**：先做半自动/手动回填与授权状态管理，再按开放平台权限接官方 API。
5. **S2 运营大脑主流程重排**：把输入、Brief、调度、验收、复盘入口组织成一条可讲清楚的路径，并基于真实账号接入状态选择任务范围。
6. **S3 清理示例数据露出**：复盘看板只保留真实指标、优化建议、送入运营大脑；其他示例图隐藏或标为待接入。
7. **S4 专家团真实感修正**：当前任务从 `AgentInvocation` / `BrainTask` 聚合，不再显示固定“等待调度”的模拟状态。
8. **S5 再回到工程验证**：完成收敛后再处理 B4 rerun_scope、F5 Playwright、Postgres downgrade/upgrade。

## 六、判断标准

这次重整完成后，系统应该让人感觉：

- 这是一个可以真实跑一轮运营任务的工作台。
- 它没有假装投流、客服、全渠道都已经完成。
- 用户知道第一步要做什么，也知道每一步为什么存在。
- 运营大脑是中心，不是众多页面中的一个页面。
