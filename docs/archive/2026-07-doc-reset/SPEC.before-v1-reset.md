## 一、目标 Objective

### 我们要做什么
构建一个面向**企业自媒体运营团队**的 Web 系统，用一个**运营大脑 / 决策 Agent**统筹 8 个专业子 Agent，完成从目标理解、任务拆解、专家调用、交付物生成、分项验收、返工重跑、发布分发、投流客服到复盘闭环的完整流程。

系统核心不是"8 个聊天机器人"，也不是固定流水线后台，而是一个可配置、可追踪、可验收的**AI 专家团**：

> 运营大脑 / 决策 Agent → 按目标动态调用账号定位、编导文案、美术提示词、视频创作、剪辑、账号运营、投流、客服 8 个专业子 Agent。

运营大脑拥有编排权：它可以根据用户目标决定调用哪些子 Agent、调用顺序、是否并行、是否返工、是否跳过某些环节；同时所有调用、输入输出、交付物、验收与重跑都必须落库、版本化、可追踪。

### 谁来用
一个**企业运营团队**，包括管理员、运营、编导、美术/视频/剪辑审核、投手、客服、审核员等角色。系统先按单团队自托管设计，支持多人协作与 RBAC 权限，后续可扩展为更完整的团队协作或多租户形态。

### 成功是什么样
- 用户可以从侧边栏进入"运营大脑"，用自然语言提出目标，系统抽取成结构化任务 Brief，用户确认后执行；
- 运营大脑能自由调用 8 个专业子 Agent，并给出可解释的调度计划、关键依据、产出摘要和下一步动作；
- 每个子 Agent 的交付物可分项验收，用户可单独通过、打回或重跑某个专业产出；
- 打回后默认由用户选择重跑范围，也可让运营大脑重新判断并生成新的重跑方案；
- 任务完成并由用户确认验收后，当前阶段关闭任务记忆；后期再考虑历史记录与长期记忆；
- 专家团有独立一级模块，默认以"列表 + 详情面板"呈现运营大脑与 8 个子 Agent 的状态、配置、产出和调度记录；
- 账号矩阵是一等结构，支持项目/品牌 → 人设/赛道组 → 平台账号 → 发布、数据、客服、投流的统一管理；
- 关键质量门（脚本合规、发布前审核、大额投放）由人确认，其余自动化等级按项目、账号组、平台和动作类型配置；
- 全程可在**本机 Windows 单机部署**跑通，后期可平滑迁移到云。

### 核心设计决策（已确认）

## 一点五、产品体验规格：运营大脑与专家团

### 1. 运营大脑主页

运营大脑是系统的固定一级入口，也是登录后的默认首页。它不是传统 dashboard，也不是普通聊天页，而是"主 Agent 对话输入 + 专家 Agent 编排任务流"的工作台。默认页面包含：

- 顶部：ChatGPT 感的大输入框，用户用自然语言提交运营目标；
- 中部：主 Agent 消息流，说明接下来调用哪个专家、为什么调用、当前完成什么；
- 下方：专家 Agent 专业身份卡片，按"唤起 → 执行 → 完成 → 交接"节奏浮现；
- 结果：专家完成后默认展示一句核心结论，详细分析、证据和建议可展开；
- 侧栏/次级区：最近调度、关键风险、模型成本、授权异常、平台数据回流状态；
- 任务列表默认按状态分组：待确认、执行中、待验收、已完成、失败；
- 任务列表支持切换按项目/账号组或任务类型分组。

### 2. 任务 Brief 与执行计划

用户用自然语言描述目标后，系统抽取结构化字段：项目、账号组、平台、周期、预算、内容目标、风险约束、期望产出、需要确认的动作。

确认页默认展示任务 Brief：

- 目标与范围；
- 拟调用的子 Agent；
- 预计产出；
- 关键风险；
- 需要人工确认的动作。

用户可展开完整计划书，查看阶段计划、每个 Agent 的输入输出、时间线和质量门。用户确认后才进入执行；高风险动作仍受自动化等级和质量门约束。

### 3. 专家团总览

专家团作为系统一级模块呈现，默认进入"专家团总览"。布局采用**列表 + 详情面板**：

- 左侧为运营大脑与 8 个子 Agent 的紧凑列表；
- 右侧为选中 Agent 的详情；
- 不采用中心辐射图或组织架构大图作为默认界面，避免炫技和低效浏览。

左侧列表按业务分组：

- **主控层**：运营大脑 / 决策 Agent；
- **策略组**：账号定位专家；
- **创作组**：编导文案专家、美术指导提示词专家、视频创作专家、剪辑专家；
- **运营执行组**：账号运营专家；
- **增长组**：投流专家；
- **用户反馈组**：客服专家。

点开任一子 Agent 后，详情第一屏优先展示当前任务：

- 当前由运营大脑分配的目标与任务；
- 所属项目、账号组、平台、内容或复盘周期；
- 当前进度、阻塞点、风险等级、预计完成时间；
- 已生成的关键产出摘要；
- 下一步动作：继续、打回、重跑、人工确认、调整输入。

同页或 Tab 中保留：

- 能力卡片：一句话能力、可调用工具、典型任务、标准输出；
- 历史产出：最近交付物、版本、质量评价、打回记录；
- 配置管理：模型、提示词、工具权限、自动化等级、可调用范围。

### 4. 编排与追踪

运营大脑默认参考链路为：

> 账号定位 → 编导文案 → 美术指导 → 视频创作 → 剪辑 → 账号运营

但该链路只是参考，不是强制流水线。复盘、投流、客服、账号诊断、爆款追踪、负面舆情处理等目标可以跳过默认链路，由运营大脑按需动态调用一个或多个子 Agent。

过程透明度采用"默认简洁、可展开完整链路"：

- 默认展示：调用了哪些子 Agent、每个 Agent 的状态、关键产出摘要、风险；
- 展开后展示：调用输入、输出、版本、日志、失败原因、动作、上下游依赖。

### 5. 验收、重跑与任务记忆

任务验收采用分项验收。用户可以按子 Agent 交付物分别通过、打回或重跑，例如脚本通过、提示词打回、投流计划重跑。

分项打回后默认由用户选择重跑范围：

- 只重跑当前 Agent；
- 连带重跑上游；
- 连带重跑下游；
- 全链重跑。

同时保留"让运营大脑重新判断"选项。运营大脑会结合用户打回原因、子 Agent 输入输出、调用日志、当前项目目标、账号定位、平台规则和质量门结果，生成建议重跑方案；界面只展示关键判断依据与建议动作，详细依据可展开。

当前阶段不做长期记忆：运营大脑只在一次任务内保留上下文，任务完成并由用户确认验收后关闭该任务记忆。后期可把过程与结果沉淀到历史记录，但本阶段不实现长期记忆库或团队偏好记忆。

### 6. 账号矩阵与多平台

多账号、多平台是一等结构，不只是账号列表：

`项目/品牌 → 人设/赛道组 → 平台账号（抖音 / 小红书 / 视频号） → 发布记录 / 授权状态 / 数据回流 / 评论客服 / 投流计划`

账号矩阵要支持：

- 同一内容在不同平台、不同账号上的版本适配与发布状态；
- 授权状态、Token 过期、API 权限不足等风险前置暴露；
- 按项目、赛道、人设、平台、账号组筛选和批量下发任务；
- 抖音先真实接入，小红书和视频号保留半自动/手动回填与未来 OAuth 接入。

### 7. UI 气质

系统 UI 走**冷白磨砂纸质感 + 黑白灰极简 + 飞书级日常易用**路线：

- 禁用"作战台、指挥室、战情"这类口号化表达；
- 第一印象高级、克制、可靠，不做模板化 SaaS 和老式国产后台；
- 默认浅色，使用冷白/雾白/石墨黑/细灰线建立高级感；深色主题仅保留为后续可选模式；
- 可以使用克制的冷白磨砂纸质背景，但不能做复古纸张、噪点装饰或默认毛玻璃卡片；
- 少做装饰，多做密度、层级、可扫读路径；
- 专家团、流程、账号矩阵、风险队列要像专业运营系统，不像功能菜单堆叠；
- 专家 Agent 默认使用专业身份卡片，不使用真人头像或卡通数字员工；
- Agent 编排过程第一阶段可先用高保真前端演示流程实现，但必须预留真实后端 Agent 接口，避免把流程硬编码在页面组件里。

## 二、技术栈 Tech Stack

### 后端
- **语言 / 框架**：Python 3.11+，FastAPI（async）
- **数据库**：PostgreSQL 16（业务数据 / 交付物 / 版本 / 任务 / 审批 / 知识库）
- **ORM / 迁移**：SQLAlchemy 2.x（async）+ Alembic
- **缓存 / 事件总线 / 队列**：Redis 7 + **arq**（asyncio 原生任务队列，跨平台、对 Windows 友好；不选 Celery 以规避 Windows 兼容坑）
- **对象存储**：v1 用本地磁盘卷；预留 **MinIO**（S3 兼容）接口，迁云即换 OSS/COS，不改业务代码
- **数据校验 / Schema**：Pydantic v2（交付物 payload 统一用 Pydantic 模型校验）
- **Agent 编排**：运营大脑 / 决策 Agent + 动态编排引擎 + 事件驱动；M1 可先用自研轻量状态机跑通闭环，M1/M2 引入 **LangGraph** 作为复杂分支、持久化状态、人机确认与可恢复执行的编排适配层
- **Agent 辅助框架**：**LangChain** 仅用于模型调用封装、工具调用、结构化输出、Prompt 模板与解析器，不替代业务数据模型、权限、质量门和编排主状态
- **工具协议**：先实现内部 `ToolAdapter` 白名单；M2+ 引入 **MCP** 作为安全工具/外部系统接入协议，默认禁止任意文件、命令与无审计工具调用
- **实时推送**：WebSocket（看板状态、任务进度实时更新）
- **认证**：JWT + RBAC（角色权限）

### 前端
- **框架**：React 18 + TypeScript + Vite
- **UI**：Ant Design（中后台组件齐全，契合运营工作台）
- **状态 / 数据**：TanStack Query（服务端状态）+ Zustand（本地状态）
- **图表**：ECharts（复盘仪表盘）
- **流程可视化**：**React Flow / @xyflow/react**（任务调度图、Agent 调用链、返工依赖图、执行 Trace 展开视图）；专家团默认页仍采用列表 + 详情面板
- **实时**：原生 WebSocket / socket 客户端

### 大模型网关（多模型抽象）
统一 `LLMGateway` 接口，对内保持稳定业务 API；底层优先接入 **LiteLLM**（Proxy 或 SDK）作为多模型网关，适配：
- 国内模型：DeepSeek（**当前已有 Key，v1 默认模型**）、豆包（Doubao）、通义千问、Kimi
- Anthropic Claude（Opus / Sonnet）—— 取得授权且确认合规后接入
- 运营大脑与每个子 Agent 均可在配置中绑定首选模型 + 兜底模型；LiteLLM / `LLMGateway` 负责路由、重试、Fallback、限流、Token/成本统计、调用审计
- **v1 运营大脑与全部子 Agent 默认走 DeepSeek**；架构保持多模型，后续有 Key 再按 Agent 切换更优模型

> ⚠️ 合规：境内企业数据发往境外模型（Claude）需评估数据出境合规。系统按 Agent 配置模型，**默认创作类可选高质量模型、含真实用户/客户数据的 Agent（如客服、投流人群）优先国内模型**。具体策略见"边界"与"开放问题"。

### 外部集成（适配器层，插件化）
统一抽象接口，按现有资产分期接真实实现，其余先 stub / 手动回填：
- **AI 视频生成：Seedance（已有会员 + API Key，M1 先接真实）**、可灵、Runway 等预留
- **平台发布 / 数据：抖音开放平台（已有 API Key，M1 接发布 + 数据）**；小红书 / 视频号预留
- 投流：巨量千川（预留，M3 接入）
- 数据抓取：蝉妈妈 / 飞瓜（预留；优先用平台官方数据，第三方为补充）
- 评论 / 私信：抖音评论 API（客服，M2）

> **当前可用凭证**：DeepSeek API Key · Seedance 会员 + API Key · 抖音 API Key。这三样决定 M1 的真实集成范围。

### 部署 / 运维
- **Docker Compose** 一键编排：`backend` + `worker(arq)` + `postgres` + `redis` + `minio` + `frontend(nginx)`
- 本机 Windows 11 Pro 自托管（Docker Desktop）
- 团队访问：局域网 / 内网穿透（如 frp、cloudflared）
- 迁云：同一套 compose 上云即可，存储/凭证走环境变量

## 三、命令 Commands

> 以下为目标命令规划（脚手架建立后落地为实际脚本）。

```bash
# —— 一键启动（生产/演示）——
docker compose up -d                      # 拉起全部服务
docker compose logs -f backend worker     # 看后端与 worker 日志
docker compose down                       # 停止

# —— 后端开发 ——
cd backend
uv sync                                   # 安装依赖（用 uv 管理）
uvicorn app.main:app --reload             # 启动 API（开发）
arq app.worker.WorkerSettings             # 启动任务/事件 worker
alembic upgrade head                      # 应用数据库迁移
alembic revision --autogenerate -m "msg"  # 生成迁移（改 schema 后）

# —— 后端质量 ——
pytest                                     # 全部测试
pytest -m "not integration"               # 仅单元测试
pytest --cov=app --cov-report=term-missing # 覆盖率
ruff check . --fix                         # Lint + 自动修复
ruff format .                              # 格式化
mypy app                                   # 类型检查

# —— 前端开发 ——
cd frontend
pnpm install
pnpm dev                                   # Vite 开发服务器
pnpm build                                 # 生产构建
pnpm test                                  # vitest 单测
pnpm lint                                  # eslint
pnpm e2e                                   # Playwright 端到端
```

### 5.2 专家团 Agent（system prompt 源自配置表与产品规格）
| 编号 | Agent | 层级/分组 | 核心职责 | 主要交付物 |
|---|---|---|---|---|
| 00 | 运营大脑 / 决策 Agent | 主控层 | 理解目标、抽取任务 Brief、生成调度计划、调用子 Agent、汇总结果、处理分项验收与重跑 | 任务 Brief、调度计划、调用记录、重跑建议、执行结果摘要 |
| 01 | 账号定位专家 | 策略组 | 定位策略 / 对标拆解 / 动态监控 | 定位策略文档、对标数据库、差异化建议、定位优化报告 |
| 02 | 编导文案专家 | 创作组 | 选题策划 / 发布规划 / 脚本创作 | 选题方案、发布日历、视频脚本、分镜建议、配乐建议、制作 Brief |
| 03 | 美术指导提示词专家 | 创作组 | 视觉风格 / 结构化 AI 提示词 | 视觉风格书、AI 提示词脚本、提示词版本表、美学标准 |
| 04 | 视频创作专家 | 创作组 | AI 视频生成执行 / 素材管理 | 生成工具计划、素材交付清单、素材版本表、质量反馈 |
| 05 | 剪辑专家 | 创作组 | 后期加工 / 爆款风格 / 多平台适配 | 工程文件、成片交付清单、剪辑说明、风格库 |
| 06 | 账号运营专家 | 运营执行组 | 多平台分发 / 数据复盘 / 优化建议 | 日/周/月复盘、发布记录、数据看板、优化建议 |
| 07 | 投流专家 | 增长组 | 千川投放 / 人群定向 / ROI / 自动投放 | 投放计划、投放日/周报、人群定向效果分析 |
| 08 | 客服专家 | 用户反馈组 | 评论回复 / 负面管理 / 私域导流 / 需求反哺 | 评论日报、用户需求报告、高意向用户表、话术库 |

每个 Agent = `system prompt + 绑定模型 + 工具集 + 输入/输出 Pydantic schema + 权限/自动化等级 + 可调用范围`。运营大脑额外拥有任务规划、子 Agent 调度、分项验收处理和重跑方案生成能力。

### 5.3 编排、验收与闭环（事件驱动）
- **任务创建**：`user.goal_submitted → decision_agent.extract_brief → user.confirm_brief → orchestration.plan_created`
- **动态调度**：运营大脑根据目标自由调用子 Agent，可串行、并行、跳过、返工；默认参考链路为 `定位 → 编导 → 美术 → 视频 → 剪辑 → 运营`
- **调用追踪**：每次子 Agent 调用都生成 `AgentInvocation`，记录输入、输出、模型、token、成本、状态、失败原因和上下游依赖
- **分项验收**：每个子 Agent 交付物进入独立验收状态；用户可通过、打回、重跑；验收结果影响运营大脑下一步调度
- **重跑范围**：用户默认选择重跑当前 Agent、上游、下游或全链；也可让运营大脑重新判断并生成重跑方案，用户确认后执行
- **闭环反馈**：运营复盘、客服需求、投流效果都可形成优化建议，回流到运营大脑，再由其决定是否调用定位/编导/美术/剪辑/投流/客服等子 Agent
- **质量门**：发布、投流、删评、批量操作等高风险动作受质量门与自动化等级控制（见 5.5）

### 5.4 核心数据模型（PostgreSQL）
- `Org` / `User` / `Role`（多用户、RBAC）
- `Project`（运营项目，绑定账号/定位）、`Account`（抖音/小红书/视频号账号，**矩阵一等模型**）、`AccountGroup`（账号分组：赛道/人设/平台）
- `BrainTask`（运营大脑任务：自然语言目标、结构化 Brief、绑定项目/账号组/平台/内容对象、状态、自动化等级、验收状态）
- `OrchestrationPlan`（调度计划：拟调用 Agent、顺序/并行关系、预计产出、风险、质量门、用户确认记录）
- `AgentInvocation`（子 Agent 调用记录：输入、输出、模型、token、成本、状态、失败原因、上下游依赖）
- `ContentItem`（一条内容贯穿全链路的实例，含当前阶段、状态）
- `Deliverable`（交付物：`type` + `version` + `agent` + `status` + `payload(JSONB)`；多态：定位策略/选题/脚本/提示词/素材/成片/复盘/投流计划/客服记录…，按 type 用对应 Pydantic schema 校验）
- `DeliverableAcceptance`（分项验收：交付物通过/打回/重跑、打回原因、重跑范围、运营大脑重判建议、确认人）
- `DistributionTask` / `PublishSchedule`（分发中心：一内容→多平台/多账号的定时排期与发布状态）
- `MaterialAsset`（素材库：原始/混剪/成片，含工具处理记录）、量产任务 `BatchRemixJob`
- `ComplianceCheck`（合规检测记录：敏感词/原创度/限流风险，关联 Gate3 与发布前）
- `AgentTask`（子 Agent 任务状态机：pending / running / done / failed / blocked）
- `Event`（事件日志 / 事件溯源）
- `GateApproval`（质量门审批记录：门类型、决策、审批人、意见）
- `KnowledgeEntry`（共享知识库：爆款库 / 用户画像 / 提示词库 / 话术库，可读可写）
- `ModelConfig`（运营大脑与 per-Agent 模型配置 + 兜底）
- `IntegrationConfig`（集成凭证加密存储 + 开关）
- `MetricSnapshot`（各平台数据指标快照）、`AdPlan` / `AdSpend`（投流）

### 5.5 质量门（可配置，6 道）
| Gate | 节点 | v1 默认 |
|---|---|---|
| 1 定位审核 | 定位策略完成后 | 自动通过（可打回） |
| 2 选题审核 | 月度选题完成后 | 自动通过（可打回） |
| 3 脚本合规 | 脚本完成后（违禁词/侵权） | **强制人工** |
| 4 成片审核 | 剪辑完成后 | 自动通过（可打回） |
| 5 发布前审核 | 发布前（标题/标签/封面/导流合规） | **强制人工** |
| 6 大额投放 | 日耗>2000 的投放计划 | **强制人工** |

每道门可在后台开/关与改阈值；强制门未通过则链路阻塞（`AgentTask=blocked`）。

### 5.7 规模化执行层（借鉴易媒助手，垫在专家团智能层之下）
DyFlow 的差异化 = AI 专家团的"创作 + 决策 + 优化大脑"；但矩阵运营还需要一层"规模化执行 + 效率工具"。借鉴易媒助手补齐以下 5 项能力，与运营大脑和 8 个专业子 Agent 协同（专家团产出策略/内容，执行层负责规模化落地）：

1. **多账号矩阵管理**：账号分组（按赛道/人设/平台）、批量授权与 Token 托管、规模化运维上千账号；`Account` 升级为一等矩阵模型，新增 `AccountGroup`。运营大脑任务可按账号/分组维度批量下发。
2. **分发中心（批量发布 + 定时分发）**：一条内容 → 多平台自动适配（比例/封面/标题/标签）→ 定时排期队列批量发布；统一发布记录与状态回流。建立在平台发布适配器之上。
3. **批量混剪二创去重量产**（矩阵铺号核心场景）：剪辑 Agent 增加"批量量产模式"——基于素材自动混剪、批量二创去重，一次产出大量差异化短视频供矩阵号铺量（仍受 30% 差异化与合规约束）。
4. **素材工具集**：去水印 / 加水印 / 裁剪 / 转码 / GIF 导出等高频工具，挂在剪辑/素材模块，供量产与适配复用。
5. **合规检测服务**：独立服务 = 敏感词库检测 + 原创度/查重 + 限流风险评估；作为 **Gate 3（脚本合规）** 与发布前的强制依赖，发布/投放链路统一调用。

> 定位：执行层让专家团的高质量产出能**规模化、合规化、自动化**地落到上千矩阵账号。带货挂载（小黄车/团购）暂不做。

### 5.8 开源技术接入边界

DyFlow 需要借助成熟开源项目提高工程可靠性，但核心产品语义仍由本系统掌控：任务 Brief、专家团职责、质量门、分项验收、账号矩阵、交付物版本与审计记录都必须落在自有数据模型中，不能被外部框架黑盒化。

| 技术 / 项目 | 是否需要 | 主要用途 | 接入阶段 | 边界 |
|---|---:|---|---|---|
| **LiteLLM** | 必要 | 多模型统一网关、Fallback、限流、成本统计、虚拟 Key / 调用审计 | M0/M1 | 对外仍暴露 `LLMGateway`；业务代码不直接散落调用各模型 SDK |
| **LangChain** | 需要但克制 | Prompt 模板、工具调用、结构化输出、解析器、少量 Agent 辅助能力 | M1 | 不承载业务状态机；不替代 Pydantic schema、数据库模型、权限和质量门 |
| **LangGraph** | 必要 | 运营大脑复杂编排、人机确认、可恢复执行、分支/并行/返工、长任务状态 | M1/M2 | LangGraph 只做执行图和状态推进；`BrainTask` / `OrchestrationPlan` / `AgentInvocation` 仍是系统事实源 |
| **React Flow / @xyflow/react** | 必要 | 调度计划图、Agent 调用链、返工影响范围、Trace 展开视图 | M1/M2 | 不作为专家团默认导航；专家团默认仍是高密度列表 + 详情面板 |
| **MCP** | 需要 | 标准化接入内部工具、外部工具和未来第三方能力 | M2+ | 只开放白名单工具；必须有 RBAC、参数校验、审计日志、超时和速率限制；默认不开放任意命令/文件访问 |
| **n8n** | 可选 | 飞书/企业微信通知、Webhook、轻量低代码自动化、旁路集成胶水 | M2+ | 不能替代运营大脑编排；不能承载核心业务事实源；只做外围自动化 |
| **Dify / Flowise** | 暂不作为核心 | 原型验证、Prompt 试验、参考交互 | 视需要 | 不作为生产编排底座，避免核心流程被低代码黑盒锁死 |

落地原则：
- **先适配，再绑定**：所有外部框架都通过 adapter 接入，业务层只依赖自有接口。
- **先可审计，再自动化**：模型调用、工具调用、MCP 调用都要记录输入、输出、成本、状态、操作者与失败原因。
- **先闭环，再炫技**：M1 目标是运营大脑 + 专家团跑通端到端闭环；复杂图编排、MCP 工具生态和低代码旁路按阶段增强。
- **人机确认优先**：发布、投流、删评、批量私信、预算变更等高风险动作必须经过质量门或自动化等级配置控制。

## 六、代码风格 Code Style

### Python（后端）
- `ruff` 负责 lint + format；强制 type hints；async 优先；业务对象用 Pydantic。
- 命名：模块/函数 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE`。

```python
# backend/app/agents/base.py
from abc import ABC, abstractmethod
from pydantic import BaseModel

from app.llm.gateway import LLMGateway
from app.schemas.deliverable import DeliverablePayload


class AgentContext(BaseModel):
    content_item_id: int
    upstream: dict[str, DeliverablePayload]   # 上游交付物（按 type 取）
    knowledge: dict[str, list[dict]]          # 共享知识库切片


class BaseAgent(ABC):
    """所有 Agent 的基类：绑定 system prompt、模型、输入/输出 schema。"""

    code: str                 # 如 "01-positioning"
    system_prompt_path: str   # app/prompts/01_positioning.md
    output_schema: type[BaseModel]

    def __init__(self, llm: LLMGateway) -> None:
        self._llm = llm

    @abstractmethod
    async def run(self, ctx: AgentContext) -> DeliverablePayload:
        """执行一次工作，产出经 schema 校验的交付物。"""
        ...
```

### TypeScript（前端）
- `eslint` + `prettier`；函数式组件 + hooks；服务端状态走 TanStack Query，禁止在组件里散落 fetch。
- 命名：组件 `PascalCase`，hook `useXxx`，变量/函数 `camelCase`。

// frontend/src/pages/PipelineBoard.tsx
import { usePipeline } from "@/hooks/usePipeline";

export function PipelineBoard({ projectId }: { projectId: number }) {

## 七、测试策略 Testing Strategy

- **后端单元测试**（pytest）：Agent 输出 schema 校验、编排状态机流转、质量门逻辑、模型网关路由/兜底、集成适配器接口契约。**LLM 与外部集成全部 mock**。
- **后端集成测试**（pytest + httpx，标记 `@pytest.mark.integration`）：API 端到端、DB 落库/版本化、事件流转触发下游、闭环反馈广播。用临时 Postgres + Redis（compose 测试栈）。
- **Agent 质量测试**：交付物 schema 强校验（结构正确）+ 关键字段断言（golden）；可选 LLM-as-judge 对脚本/提示词做质量打分（人工抽检兜底）。
- **前端**：vitest + React Testing Library（组件/hook）；Playwright 跑核心流程 e2e（建项目 → 跑链路 → 审批 → 看复盘）。
- **覆盖率期望**：后端核心模块（orchestrator / agents / llm / integrations 接口）行覆盖 ≥ 80%；前端关键页面有冒烟 e2e。
- **测试位置**：后端 `backend/tests/`，前端 `frontend/src/**/*.test.tsx` + `frontend/e2e/`。

## 八、边界 Boundaries

### 始终要做 Always
- 交付物入库前必须通过对应 Pydantic schema 校验；
- 外部凭证/模型 Key 加密存储，绝不入代码库（走 `.env` / 密钥管理）；
- 敏感操作（发布、投放、隐藏/删除评论）写审计日志；
- 提交前跑测试 + lint；
- 脚本/文案过违禁词与侵权检查；
- 记录每次 LLM 调用的模型、Token、成本。

### 先问再做 Ask First
- 新增依赖；
- 改数据库 schema（生成迁移）；
- 接入 / 改动任一外部真实 API（发布、千川、视频生成、数据抓取）；
- 改动 Agent 编排链路或质量门默认策略；
- 改动 Agent 的核心 system prompt（源自配置表）；
- 放开/关闭强制质量门；
- 配置真实投放预算/出价；
- 让含真实用户/客户数据的 Agent 使用境外模型（数据出境合规）。

### 绝不要做 Never
- 提交任何密钥/凭证/Cookie 到仓库；
- 绕过强制质量门直接发布或投放；
- 未授权搬运/二次发布他人内容（二创差异化 <30% 视为搬运）；
- 删除失败的测试来"让 CI 变绿"；
- 在未确认合规前把企业敏感数据发往未授权的境外模型；
- 在评论区与用户争论 / 违反平台规则的导流（用合规话术与替代策略）。

## 九、分期路线图（设计方建议，待确认）

> 高度自动化是目标，但所有真实集成一次做完工程量巨大。建议按"垂直切片"分期，每期都能端到端跑通。

- **M0 地基**：脚手架（compose/CI）、认证 + RBAC、核心数据模型（含 `Account`/`AccountGroup`、`BrainTask`、`OrchestrationPlan`、`AgentInvocation`、`DeliverableAcceptance`）、`LLMGateway` + LiteLLM 接入骨架、事件总线 + arq、动态编排引擎骨架、`ToolAdapter` / MCP 边界设计、前端工作台骨架。
- **M1 运营大脑 + 专家团基础闭环（v1 核心）**：运营大脑作为登录后默认首页、自然语言目标输入、主 Agent 编排专家 Agent 的可视化任务流、结构化任务 Brief、计划确认、动态调用 8 个子 Agent（默认 DeepSeek/mock 集成可跑通）、LiteLLM 多模型路由与成本统计、LangChain 结构化输出/工具调用辅助、专家团总览（列表 + 详情面板）、React Flow 调用链 / Trace 展开视图、调用记录、交付物落库 + 版本化、分项验收、打回重跑范围选择、6 道质量门、共享知识库、**富可视化复盘看板**。
  - 外部集成（用现有凭证）：**AI 视频生成接 Seedance（真实）**；**抖音接发布 + 数据回流（真实）**；小红书/视频号、千川、第三方数据抓取**先做适配器接口 + 手动回填**。
  - 执行层（借鉴易媒）：**矩阵管理（账号分组/批量授权）**、**合规检测服务（敏感词+原创度，接 Gate3）**、**素材工具集（去/加水印、裁剪、转码、GIF）** 上线。
- **M2 分发与量产**：LangGraph 复杂编排适配落地（长任务、人机确认、可恢复执行、复杂返工图）；MCP 白名单工具接入；n8n 作为通知/Webhook/低代码旁路自动化可选上线；**分发中心（一键批量发布 + 定时排期，多平台/多账号）**；**批量混剪二创去重量产模式**；补齐小红书/视频号发布；抖音评论抓取 + **客服 Agent** 上线（评论回复/负面管理/私域导流/需求反哺）；接入第三方数据抓取（蝉妈妈/飞瓜，作为官方数据补充）。
- **M3 投流自动化（暂缓）**：千川 API + **投流 Agent**、自动投放规则引擎、投流 ROI 监控均保留为后续能力；按 2026-07-02 计划调整，本轮不实现真实投放或预算自动化。
- **M4 自动化与历史智能**：全链路事件/定时触发；告警 + 成本看板；A/B 与"内容效果预测模型"；在用户确认后引入历史记录与可控长期记忆。

## 十、成功标准 Success Criteria（可验证）

- [ ] 团队成员可登录系统、按角色权限访问对应功能；
- [ ] 可创建一个运营项目并绑定账号信息、账号组和平台；
- [ ] 用户可从侧边栏进入"运营大脑"，输入自然语言目标并生成结构化任务 Brief；
- [ ] 用户确认任务 Brief 后，运营大脑可生成调度计划并动态调用一个或多个子 Agent；
- [ ] 子 Agent 调用记录可追踪输入、输出、状态、模型、成本、失败原因和上下游依赖；
- [ ] 每个子 Agent 交付物经 schema 校验后落库 + 版本化，并支持分项验收；
- [ ] 分项打回后，用户可选择重跑当前 Agent、上游、下游或全链，也可让运营大脑重新判断并确认执行；
- [ ] 强制质量门（脚本合规/发布前/大额投放）会阻塞链路并在前端出现待审批，审批通过后继续；其余门自动通过且可一键打回；
- [ ] 运营专家完成复盘后，优化建议回流给运营大脑，由运营大脑决定是否调用相关子 Agent，前端可见"建议 → 执行 → 验证"的追踪；
- [ ] **复盘看板提供富可视化图表**（趋势/对比/排名/时段热力/平台对比/ROI/情感/漏斗等），支持日/周/月切换与报告导出；
- [ ] 运营大脑与每个子 Agent 的模型可在配置页独立切换（v1 默认 DeepSeek），调用成本可在看板查看；
- [ ] LiteLLM / `LLMGateway` 能统一路由至少 DeepSeek + 一个 mock/备用模型，并记录 Token、成本、Fallback、失败原因；
- [ ] LangChain 仅作为结构化输出、Prompt 和工具调用辅助层使用，核心任务状态仍由自有数据模型和编排引擎记录；
- [ ] React Flow 可展示运营大脑调度计划、Agent 调用链、返工影响范围和可展开 Trace；
- [ ] LangGraph 接入后，复杂任务可以恢复执行、人机确认、分支/并行和返工，但系统事实源仍落在 `BrainTask` / `OrchestrationPlan` / `AgentInvocation`；
- [ ] MCP 工具调用只允许白名单工具，具备 RBAC、参数校验、超时、审计日志和失败回滚策略；
- [ ] 外部集成均通过统一适配器接口接入，新增/替换实现不改动编排主流程；
- [ ] 支持账号分组的**矩阵管理**，运营大脑任务可按账号/分组批量下发；
- [ ] **合规检测服务**（敏感词+原创度）接入 Gate3，不通过则脚本链路阻塞；
- [ ] **分发中心**可一条内容定时批量发布到多平台/多账号并回流状态（M2）；
- [ ] `docker compose up` 可在本机 Windows 一键拉起全部服务并访问工作台；
- [ ] 后端核心模块测试覆盖 ≥ 80%，核心流程有 e2e。
