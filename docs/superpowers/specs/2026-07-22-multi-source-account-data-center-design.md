# 同舟行多源账号数据中心设计

## 1. 背景与目标

抖音网站应用当前无法稳定获取完整账号历史数据、作品指标和粉丝画像。与此同时，抖音创作者后台提供的数据分散在可导出的 Excel、不可导出的诊断页面、粉丝画像页面和系统内部发布记录中。

本设计将系统从“等待单一官方接口”改为“多源信息聚合”：Excel/CSV、截图识别、人工录入、系统任务记录以及未来可能恢复的官方接口都先进入统一标准化数据层。运营复盘、运营大脑和专家 Agent 只读取统一数据视图，不直接依赖具体来源。

第一阶段目标：

- 让内测团队通过人工辅助方式建立真实账号数据档案。
- 支持作品明细、账号趋势、粉丝画像和同类基准四类数据。
- 每条正式数据均可追溯到来源、统计周期、导入人和原始证据。
- 未来接入小程序或其他官方数据源时，不重写复盘页面和 Agent 上下文。

小程序开发不属于本阶段范围，仅保留数据源适配接口。

## 2. 核心原则

1. **事实与推断分离**：平台导出、截图确认和人工录入属于事实数据；Agent 推断只能作为分析结论，不能写入事实指标。
2. **原始证据不可丢失**：解析后的结构化数据必须能够追溯到原始文件、截图或人工录入批次。
3. **不静默覆盖**：同账号、同日期、同指标出现多个来源时保留全部观测，并通过解析规则生成统一视图。
4. **先预览后入库**：文件解析和截图识别必须先展示校验预览，用户确认后才能写入正式快照。
5. **按账号隔离**：所有数据必须绑定组织、客户、项目范围内的真实账号，并复用现有账号访问控制。
6. **来源无关消费**：复盘和 Agent 读取标准化查询服务，不按 Excel、截图或未来 API 分支实现业务逻辑。

## 3. 数据源

第一阶段支持以下来源：

| 来源 | 标识 | 可信度 | 处理方式 |
| --- | --- | --- | --- |
| 抖音后台导出文件 | `platform_export` | 高 | 自动识别模板、字段映射、预览确认 |
| 截图识别并人工确认 | `screenshot_verified` | 中高 | 视觉模型提取、可编辑确认 |
| 结构化人工录入 | `manual_entry` | 中 | 表单校验、明确统计周期 |
| 同舟行系统任务与发布记录 | `system_event` | 高 | 系统自动写入，不伪造平台指标 |
| 未来官方接口 | `official_api` | 最高 | 通过统一适配器写入标准化快照 |

演示数据不得进入生产统一视图。未经过人工确认的截图识别结果不得成为正式数据。

## 4. 数据域

### 4.1 导入批次 `DataImportBatch`

记录一次完整采集行为：

- `org_id`、`account_id`、可选 `project_id`
- 来源类型和导入方式
- 统计开始、结束日期
- 导入人、创建时间、确认时间
- 原文件名、文件哈希、解析器版本
- 状态：`uploaded / parsed / needs_review / committed / failed / reverted`
- 总行数、成功数、警告数、失败数
- 失败摘要和撤销信息

批次确认后产生正式快照；撤销批次仅撤销该批次产生的观测，不删除审计和原始证据记录。

### 4.2 原始证据 `DataArtifact`

保存原始文件或截图的元数据和存储引用：

- `batch_id`
- `artifact_type`：Excel、CSV、截图
- 原始文件名、MIME 类型、大小、SHA-256
- 对象存储或受控文件存储路径
- 上传人和保留策略

数据库不直接保存大文件二进制；保存结构化数据、文件元数据和受控存储引用。

### 4.3 账号指标快照 `AccountMetricSnapshot`

用于账号日趋势和周期诊断：

- 统计日期或统计周期
- 播放量、投稿量、粉丝总数、粉丝净增
- 主页访问、互动指数
- 完播率、点击率、2 秒跳出率、5 秒完播率、平均播放时长
- 来源、批次、可信度和确认状态

字段允许为空，禁止用 `0` 代替“来源未提供”。

### 4.4 平台作品记录 `PlatformContentRecord`

作品本身与某次统计结果分开存储，避免每次导入都创建一条“新作品”：

- 账号、平台和内容类型
- 平台作品 ID、分享链接、可选同舟行内容 ID
- 标题、发布时间、审核/公开状态
- 首次发现批次、最近确认批次和原始行引用

平台作品 ID 或分享链接是强标识。当前抖音导出的“作品列表”不提供这两个字段时，系统使用“账号 + 发布时间 + 标准化标题”生成候选弱标识，但不得直接断言两条记录是同一作品：

1. 发布时间和标准化标题均唯一匹配时，允许自动关联并标记 `identity_confidence=provisional`。
2. 同一候选命中多条作品、标题被修改或发布时间缺失时，进入人工消歧，不写入正式指标。
3. 后续取得平台作品 ID 或分享链接时，将其补充到既有记录并提升为 `confirmed`，不重建历史快照。

### 4.5 作品指标快照 `ContentMetricSnapshot`

在现有 `MetricSnapshot` 基础上向后兼容演进：

- `platform_content_record_id`、统计日期或统计周期
- 播放、曝光、点赞、评论、分享、收藏
- 完播率、5 秒完播率、2 秒跳出率、封面点击率、平均播放时长
- 主页访问量、粉丝增量
- 来源、批次和原始行引用

同一作品可保留多个统计日期的快照，用于发布后 24 小时、3 天和 7 天观察。

### 4.6 粉丝画像快照 `AudienceProfileSnapshot`

采用“维度 + 项目 + 占比”结构，避免为每种画像建列：

- 统计周期
- 维度：性别、年龄、地域、设备、兴趣
- 项目：男性、女性、`<23`、广东、苹果、随拍等
- 数值和单位
- 来源截图、确认人和确认时间

### 4.7 同类基准快照 `BenchmarkSnapshot`

保存账号诊断页面中的自身值和同类作者对比：

- 指标代码和名称
- 自身值、同类值
- 高于或低于同类作者比例
- 同类范围说明
- 统计周期和来源证据

## 5. 标准化与冲突解析

每个来源通过 `DataSourceAdapter` 输出统一观测：

```text
detect(input) -> parse(input) -> normalize(rows) -> validate(rows) -> preview -> commit
```

适配器负责模板识别和字段转换，不直接决定最终业务结论。

同账号、指标和统计时间出现冲突时：

1. 保留全部观测和原始证据。
2. 默认可信度顺序为 `official_api > platform_export > screenshot_verified > manual_entry`。
3. 同一可信层级优先采用确认时间更晚且统计周期更精确的数据。
4. 差异超过指标配置阈值时创建 `DataConflict`，统一视图显示警告。
5. 用户可指定采用某个来源；人工决议必须记录决议人、时间和原因。

统一查询服务 `AccountDataViewService` 返回解析后的数据、来源摘要、数据时效、完整度和冲突，不让页面或 Agent 自行实现优先级。

## 6. 导入体验

### 6.1 入口

账号矩阵每个账号提供“数据中心”动作；运营复盘在数据缺失或过期时提供“更新数据”入口。两处进入同一账号数据中心。

### 6.2 文件导入

流程为：

1. 选择或确认当前账号。
2. 上传 Excel/CSV。
3. 自动检测文件类型和模板版本。
4. 显示统计周期、字段映射和数据预览。
5. 标记缺失值、异常百分比、非法日期和重复记录。
6. 用户修正映射或确认。
7. 原子提交批次并刷新账号数据状态。

已识别的首批抖音模板：

- 每日播放量趋势：日期、播放量。
- 单条作品表现：视频名称、发布时间、播放量、5 秒完播率、2 秒跳出率、平均播放时长。
- 作品列表：作品名称、发布时间、体裁、审核状态、播放量、完播率、5 秒完播率、封面点击率、2 秒跳出率、平均播放时长、点赞、分享、评论、收藏、主页访问和粉丝增量。
- 周期聚合表现：体裁、垂类、投稿量、点击率、完播率、跳出率、播放时长、播放中位数、点赞、评论和分享。

未知模板不能直接入库；用户可选择字段映射后保存为组织级模板。

导入作品级模板时，预览必须额外显示“作品匹配”列，区分自动关联、待确认和新建候选。只有强标识或无歧义弱标识才能提交；待确认记录必须先由用户选择既有作品或确认新建。

### 6.3 截图录入

流程为：

1. 上传一张或多张截图。
2. 用户选择或由系统识别页面类型：账号诊断、粉丝画像、其他。
3. 视觉模型提取结构化候选数据，并给出字段级置信度。
4. 左侧显示原图，右侧显示可编辑字段。
5. 低置信度字段必须人工填写或确认。
6. 用户确认统计周期后提交。

没有可用视觉模型时，保留相同双栏界面，降级为参照截图的结构化手工录入，不阻断业务。

### 6.4 手工录入

手工录入按数据域提供小型表单，不提供一个无限制 JSON 编辑器。必填账号、统计周期和来源说明。百分比按用户看到的百分数录入，后端标准化为小数。

### 6.5 批次历史

数据中心展示：

- 数据覆盖周期和最后更新时间
- 各来源贡献范围
- 导入批次、处理状态和错误报告
- 冲突数量、撤销动作和审计记录

## 7. 复盘与 Agent 消费

运营复盘从统一数据视图读取：

- 账号趋势
- 作品排名和生命周期表现
- 粉丝画像
- 同类基准
- 数据缺失、冲突和时效提示

Agent 上下文必须包含：

- `data_as_of`
- `coverage_period`
- `sources`
- `completeness`
- `conflicts`
- 被引用的数据证据 ID

Agent 的事实性结论必须引用证据；数据不足时应降低结论强度并提出补充数据建议。不得把模型推断回写为账号事实。

## 8. 权限、安全与审计

- 读取和导入沿用客户、项目和账号授权边界。
- 运营负责人和运营人员可导入；审核员默认只读；管理员可撤销批次。
- 文件类型、大小、压缩包内容和公式风险必须在服务端校验。
- Excel 仅读取值，不执行宏、外链或公式。
- 原始文件不可公开访问，下载必须经过鉴权。
- 上传、解析、确认、冲突决议和撤销均写入事件账本。
- 日志不记录原始文件内容或敏感账号数据。

## 9. 数据时效与产品提示

建议节奏：

- 首次建立账号档案：导入最近 30 天数据。
- 固定周复盘：每周导入上周数据。
- 重点作品：发布后 24 小时、3 天和 7 天补充快照；内测初期可只保留 7 天节点。
- 数据超过 7 天未更新时提示“建议更新”，但允许用户明确选择使用旧数据继续。

页面必须展示“最后更新于”和来源，不使用含糊的“数据正常”状态。

## 10. 兼容与未来扩展

- 保留现有复盘 API 的兼容响应，在统一查询服务就绪后逐步切换实现。
- `MetricSource` 扩展为细粒度来源，旧 `manual` 和 `douyin` 数据通过迁移映射。
- 未来小程序、官方 API 或第三方平台只需新增 `DataSourceAdapter`。
- 新来源必须通过相同预览、校验、证据、冲突和权限规则。

## 11. 第一阶段验收标准

1. 四种现有抖音 Excel 均能被识别并显示正确预览，包括 68 条数据行的“作品列表”模板。
2. 用户可从截图参照界面录入账号诊断与粉丝画像。
3. 所有正式数据均绑定账号、统计周期、批次和原始来源。
4. 重复导入不会重复累计，冲突不会被静默覆盖。
5. 批次可撤销，审计仍保留。
6. 运营复盘能展示人工导入的真实趋势、作品表现、画像和基准。
7. 运营大脑能读取统一数据并明确展示数据时间与来源。
8. 没有数据、数据过期或存在冲突时，系统提供准确提示，不显示 Mock 结果。
9. 缺少平台作品 ID 和链接时，系统不会仅凭相似标题错误合并作品；歧义记录必须进入人工消歧。

## 12. 非目标

- 本阶段不开发抖音小程序。
- 不使用浏览器自动化抓取抖音后台。
- 不承诺恢复已下线的网站应用粉丝或视频数据接口。
- 不允许未确认的 OCR/视觉识别结果自动进入正式复盘。
- 不在第一阶段建设通用数据仓库或复杂 BI 自助分析器。
