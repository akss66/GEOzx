# Smart Agent Loop Interaction Design

> 状态：用户已确认
> 日期：2026-07-17
> 适用范围：运营大脑前后端、全局主 Agent 入口、专家独立调用后的主 Agent 接力
> 参考：Grok Build 的父会话、隔离子 Agent、受控工具调用、可恢复会话、后台任务与上下文压缩思路；仅借鉴架构与产品模式，不复制源码。

## 0. Grok Build 深度参考映射

本轮参考对象是 `xai-org/grok-build` 的 Agent 产品与运行时设计，不是其 Rust TUI、编码工具或终端外观。映射关系固定如下：

| Grok Build 模式 | 同舟行落点 | 产品表现 |
| --- | --- | --- |
| 父会话是持续任务的事实来源 | `BrainTask.thread_id + Event` | 刷新、补充要求、暂停和恢复始终回到同一条运营会话 |
| 子 Agent 使用隔离上下文与受限工具集 | `AgentInvocation` 输入包、独立 prompt、工具白名单、输出契约 | 专家只读取当前客户、项目、平台和账号，不共享无关上下文 |
| 子 Agent 生命周期在父会话原位更新 | `subagent_started/progress/completed/failed` 事件投影 | 专家身份先浮现，运行中更新状态，完成后在同一位置显示核心结论 |
| 父 Agent 只接收压缩后的子 Agent 结论 | 专家 `output_summary + artifact refs` | 主 Agent 不把原始 JSON 和完整工具日志重新塞回对话 |
| 权限逐动作判断、最小范围授权 | `AgentToolCall.permission_mode` 与审批账本 | 输入器原位变身，只批准当前动作；拒绝意见成为下一轮约束 |
| 会话可继续、恢复、压缩和回看 | `Event` 追加式时间线与 compact 事件 | 页面重载不丢失消息、专家状态、方案选择和权限暂停点 |
| 后台任务具有实时状态并可稍后取回 | invocation 状态、耗时和最终结果 | 长分析不阻塞输入，用户可继续补充，完成后结果回到原会话 |
| 计划确认是结构化交互 | `DecisionRequest` | 方案在对话内选择、换一批或自定义，不使用突兀大弹窗 |

额外约束：专家只能由主 Agent 派发，第一阶段不允许专家继续派发专家，避免递归失控。专家详情可展开或进入独立详情，但父会话只保留身份、状态、接力关系、核心结论和正式成果入口。

### 0.1 主 Agent 是唯一控制平面

- 主 Agent 对工作流拥有唯一调度权：是否调用能力、调用哪位专家、并行还是串行、是否改派、是否继续以及何时结束，都必须由主 Agent 在当前轮根据目标、上下文和最新观察动态决定。
- 旧 `OrchestrationPlan.steps` 只能作为兼容账本和执行记录，不能再决定首批专家或预置固定接力顺序。
- 意图识别只负责区分普通交流、澄清、分析、工作流和外部动作，不得借机把一组专家固化成待执行流水线。
- 专家是受控执行单元：接收主 Agent 下发的隔离任务包，使用自己的 system prompt、数据范围和工具白名单，返回结构化成果；专家无权派发其他专家或修改父任务。
- 主 Agent 的控制权不高于人工审批、安全策略、租户/客户/项目/账号权限和预算上限，这些规则属于不可绕过的运行时护栏。

### 0.2 统一能力注册表与 MCP 扩展面

主 Agent 不面向硬编码专家顺序，而面向统一的 `Capability Registry`。每项能力至少声明：

- `kind`：`expert`、`tool` 或未来的 `mcp_server` / `mcp_tool`。
- `code`、业务名称、职责描述和输入/输出契约。
- 当前组织是否启用、可访问的数据边界、工具权限模式和风险等级。
- 是否可并行、是否需要前置观察、是否触发人工确认。

当前阶段先把现有八位专家接入该注册表；后续 MCP 只新增适配器和能力条目，不改变主 Agent 的 `decide -> dispatch -> observe -> decide` 主循环。

## 1. 目标

把运营大脑从“根据关键词生成一次固定专家计划”的任务启动器，升级为一个持续观察、动态编排、可讨论、可选择、可暂停和可恢复的主 Agent。

用户应当感受到：

1. 主 Agent 先理解用户真正想做什么，而不是一收到消息就机械调用专家。
2. 专家只在有明确价值时出现，并且主 Agent 会根据专家结果决定下一步。
3. 方案选择和风险授权在同一对话内完成，但二者具有不同交互语义。
4. 执行过程灵动、清楚、有节奏，不把日志、原始 JSON 或模型名称倾倒给业务用户。

## 2. 已确认的关键决策

### 2.1 智能混合模式

主 Agent 采用“模型判断 + 规则护栏”的智能混合路由：

- 模型负责理解意图、判断信息是否充分、选择专家和决定下一步。
- 规则负责账号与项目边界、权限、风险、预算、最大轮次和不可绕过的质量门。
- 普通问候、简单问答和讨论不创建专家工作流。
- 信息不足时只追问一个最关键问题，不展示 Brief 表单。
- 目标足够明确时可以先执行低风险分析，不要求用户预先填写完整表单。
- 规划或模型失败时不得静默回退到固定专家组合。

### 2.2 权限确认采用 B：输入框临时变身

当工具、发布包、外部平台动作或正式写入需要授权时：

- 页面不弹出大窗口，不在输入框上方堆叠独立大卡片。
- 底部对话输入器原位切换为紧凑的“确认模式”。
- 首屏只显示动作、对象、影响和风险等级。
- 操作包括“驳回”“修改要求”“允许”。
- 点击“修改要求”后，当前输入器在原位展开文本输入，提交后记录为重跑要求。
- 完整工具参数、成本、耗时和审计信息只进入“执行详情”。
- 处理完成后输入器平滑恢复普通对话模式。

### 2.3 方案选择采用 B：对话内结构化选项

当存在多种合理运营方案时，主 Agent 在对话流中生成结构化决策对象：

- 显示问题、选择原因和 2 至 4 个互斥方案。
- 每个方案显示标题、一句说明、主要收益和主要代价。
- 主 Agent 可以标记一个“建议方案”，但不能替用户自动确认。
- 用户可以直接选择、要求再给一组方案，或输入自己的方向。
- 选择完成后，决定作为 runtime 事件保存，主 Agent 从该决定继续执行。
- 方案选择不是权限审批，不使用“允许 / 驳回”文案。

## 3. 主 Agent 行为模型

### 3.1 意图分类

服务端是意图判断的唯一事实来源。每条用户消息被归入：

- `conversation`：问候、解释、简单问答。
- `clarification`：目标存在，但缺少一个会改变执行方向的关键信息。
- `analysis`：可以直接进行的低风险分析。
- `workflow`：需要专家、工具或多阶段成果的运营任务。
- `action`：包含正式写入、发布准备、外部平台或其他受控动作。

分类结果至少包含：

- `intent`
- `confidence`
- `reason`
- `missing_field`
- `clarifying_question`
- `suggested_expert_codes`
- `requires_account_context`

前端不得再次使用关键词复制一套意图分类，也不得生成本地罐头式主 Agent 回复。

### 3.2 动态 Agent Loop

LangGraph 主运行时调整为：

```text
加载上下文
  -> 理解意图
  -> 必要时追问
  -> 决定下一步
  -> 从能力注册表选择并派发 0-N 位专家/工具
  -> 观察专家结果
  -> 重新决定下一步
  -> 方案选择或权限门
  -> 汇总完成
```

运行约束：

- 第一轮也必须由主 Agent 实时决策，禁止从旧计划或关键词映射直接取“默认首批专家”。
- 每轮只选择当前最有价值的 0 至 N 项能力。
- 无依赖的专家可以并行，有依赖的专家明确接力。
- 专家使用隔离上下文、独立 system prompt、工具白名单和输出契约。
- 每轮完成后，主 Agent 读取压缩后的专家结论，而不是把全部原始输出重复塞回上下文。
- 主 Agent 可以继续调用专家、询问用户、发起方案选择、发起权限请求或结束任务。
- 默认最大 6 轮、单轮最多 3 位专家；达到预算或轮次上限时必须解释并请求用户决定。
- 用户可随时输入补充、打断、修改方向或要求继续；后续消息进入同一 thread。

### 3.3 失败与恢复

- 意图模型失败：使用安全的直接回复或可见重试，不默认调用定位与内容专家。
- 专家失败：保留已完成结果，显示业务化失败原因，并由主 Agent判断重试、换专家或询问用户。
- 工具失败：记录脱敏错误、重试次数和下一步，不丢失 task/thread。
- 页面刷新：从 `BrainTask + Event + AgentInvocation + AgentToolCall` 恢复对话和暂停点。
- 上下文过长：生成可审计的压缩事件，保留目标、用户决定、关键成果、待办和权限状态。

## 4. 数据与接口设计

### 4.1 继续复用现有账本

- `BrainTask`：会话和运行主对象。
- `Event`：用户消息、主 Agent 消息、专家接力、决策、暂停、恢复和压缩时间线。
- `AgentInvocation`：每次专家调用。
- `AgentToolCall`：工具请求、权限和结果。
- `DeliverableAcceptance`：正式成果验收。

第一阶段不新增独立工作流数据库，不引入 Celery/Redis。

### 4.2 新增结构化对象

`IntentDecision`：

```json
{
  "intent": "workflow",
  "confidence": 0.91,
  "reason": "用户要求分析账号并给出下周选题",
  "missing_field": null,
  "clarifying_question": null,
  "suggested_expert_codes": ["01-positioning", "06-operation"],
  "requires_account_context": true
}
```

`RuntimeNextStep`：

```json
{
  "action": "dispatch_experts",
  "expert_codes": ["01-positioning", "06-operation"],
  "rationale": "需要同时核对定位与近期表现",
  "handoff_message": "我会让账号定位专家和账号运营专家并行核对。"
}
```

`DecisionRequest`：

```json
{
  "id": "decision-12",
  "title": "下周内容优先采用哪条主线？",
  "summary": "两条路线都符合账号定位，但资源投入不同。",
  "choices": [
    {
      "id": "authority",
      "title": "专业权威线",
      "description": "强化参数拆解与避坑内容。",
      "benefit": "更稳地积累信任",
      "tradeoff": "增长速度相对慢",
      "recommended": true
    }
  ],
  "allow_custom_input": true,
  "status": "pending"
}
```

### 4.3 API

保留现有接口并新增：

- `POST /brain/messages`：向当前 thread 发送普通对话、补充或打断消息；服务端统一分类。
- `POST /brain/tasks/{id}/decisions/{decision_id}/select`：选择一个方案。
- `POST /brain/tasks/{id}/decisions/{decision_id}/revise`：提交自定义方向或要求重给方案。
- `GET /brain/tasks/{id}/runtime`：继续返回 timeline、专家、工具、成果，并增加 `pending_decisions` 与 `intent`。

权限审批继续使用现有 tool-call approve/reject 接口，但前端以输入器确认模式呈现。

## 5. 前端体验

### 5.1 对话优先级

默认只显示：

1. 用户消息。
2. 主 Agent 流式回复。
3. 专家身份、状态、接力说明和一句核心结论。
4. 可展开的完整专家分析或正式成果。
5. 方案选择对象。
6. 当前输入器状态。

原始 JSON、模型名、内部枚举、完整工具参数和重复状态事件不进入主对话。

### 5.2 专家入场与接力

- 主 Agent 先用自然语言说明为什么调用专家。
- 专家身份字标在 180-240ms 内淡入并轻微上移。
- 运行中的专家只在状态点使用低幅度呼吸，不让整张卡持续闪动。
- 并行专家并排显示紧凑状态，结果按完成顺序进入对话。
- 接力时显示一条短过渡，例如“定位已明确，接下来交给内容策略专家”。
- 专家结果默认呈现“一句核心结论 + 展开完整分析”。

### 5.3 流式输出

- 主 Agent 和专家正文都消费真实后端 token/event 流。
- 尚未发生的专家调用不得在前端预演。
- 断流时保留已收到文本，显示重连或继续入口。
- 状态变化使用事件驱动，不用前端计时器伪造完成。

### 5.4 动效约束

- 只为状态变化、身份入场、接力和输入器模式切换服务。
- 禁止粒子、光球、无意义循环动画和大面积弹跳。
- 所有动画提供 `prefers-reduced-motion: reduce` 降级。
- 动效不得改变固定布局尺寸，避免对话跳动。

## 6. 安全、权限与范围

- 未明确选择账号时，涉及账号数据的分析或任务必须追问/阻断，不取第一个账号兜底。
- 专家只能读取当前客户、项目和账号范围。
- 外部平台、发布、正式写入和项目规则要求的动作进入权限门。
- 方案选择不等于授权；选择策略后若后续动作高风险，仍需单独确认。
- 移动端本轮不实现，桌面端为唯一验收范围。

## 7. 非目标

- 不在本轮接入新的外部平台或自动发布权限。
- 不建设完整通用工作流设计器。
- 不展示思维链或模型内部推理。
- 不复制 Grok Build 的编码工具、终端 UI 或源码实现。
- 不为“灵动”加入与任务无关的装饰动画。

## 8. 验收场景

1. 用户发送“你好”：只有主 Agent 自然回复，专家调用数为 0。
2. 用户发送含糊目标：主 Agent 只追问一个会改变执行方向的问题。
3. 用户要求分析当前账号并制定下周内容：主 Agent 选择必要专家，显示真实流式回复和接力。
4. 第一轮专家完成后，主 Agent 根据结论决定是否需要下一位专家，不执行预设全链路。
5. 存在两个合理策略：对话中出现结构化方案选择，用户选择后 runtime 继续。
6. 即将生成发布包：底部输入器原位进入确认模式；修改、驳回、允许均可恢复 runtime。
7. 刷新或断流后：已完成文本、专家状态、方案选择和权限暂停点均可恢复。
8. 业务主界面不出现原始 JSON、内部模型名或固定专家兜底的假调用。
