# 同舟行系统体验重构设计

> 日期：2026-07-16
> 状态：待用户书面验收
> 来源：逐题产品与设计访谈
> 约束：本文替代旧前端设计方案；已落地后端能力和真实数据必须保留。

## 1. Why

现有系统已经具备 OAuth、账号、Agent Runtime、内容、审批、指标、成本和知识库等后端骨架，但前端仍表现为传统后台：模块割裂、卡片过多、空状态巨大、技术细节外露，运营大脑也没有成为真正的工作入口。

此次重构不是换主题，而是同时重建：

1. 产品信息架构。
2. Agent 交互模型。
3. 模块工作区。
4. 品牌设计系统。
5. 前后端交付与验收方式。

## 2. Confirmed Decisions

### Product

- 第一用户是管理多个客户、项目和账号的代运营团队。
- 客户拥有长期账号资产，项目可关联多个账号，账号可参与多个项目。
- 第一阶段仅供团队内部使用，不建设客户门户。
- 后期商业化预留多租户、计费和外部协作能力，但不进入本阶段实现。

### Agent

- 主 Agent 自主选择专家、工具和顺序，不按固定流水线机械调用。
- 普通问候不会触发专家团队。
- 主 Agent 全局随行，但只在用户召唤、发现风险或需要确认时主动出现。
- 专家可独立调用并产出正式结果。
- 专家结果必须由用户确认后才能写入正式业务数据。
- 专家采用“编辑部身份体系”：职能代号、字标、职责和接力编号，不使用虚构真人头像。
- 默认对话只展示业务过程，完整技术执行详情折叠。

### Navigation and context

- 第一阶段保留当前一级导航名称。
- 运营大脑使用全局系统导航 + Claude / ChatGPT 式大对话区。
- 左上角切换客户与项目，顶部紧凑显示平台和账号。
- Agent 只能建议上下文切换，用户确认后执行。

### Modules

- 账号矩阵：表格、矩阵、卡片、项目四种视图。
- 内容生产：默认文档画布，素材、版本、阶段、审批和 Agent 按需展开。
- 人工审批：左队列、中预览、右风险和操作的三段式工作台。
- 运营复盘：目标 → 变化 → 归因 → 建议 → 下一轮任务。
- 知识库：人工维护，Agent 建议沉淀，用户确认后写入。
- 使用成本：运营负责人和技术管理员两层视图。
- 管理中心：专家管理与模型基础设施分离。

### Visual

- 当前登录页是品牌起点，不是所有页面的布局模板。
- 全局采用暖纸品牌框架 + 柔白工作画布。
- 使用墨黑强排版和克制品牌红。
- 卡片只用于真正独立对象，不做页面章节卡片墙。
- 运营大脑和成果揭示允许强表现力；管理页面保持稳定高效。
- 首版只做浅色主题。

### Delivery

- 正式环境只展示真实数据。
- 每个模块前后端一起实现。
- 每个模块必须先确认高保真稿，再实现和 localhost 验收。
- 用户明确批准后才能部署线上。

## 3. Experience Architecture

### Global entry

登录后进入全局运营入口：

- 运营大脑是主要入口。
- 全局摘要只显示客户任务数、待审批和风险，不展示跨客户业务内容。
- 进入客户 / 项目后，所有 Agent、内容、知识和数据严格限定在当前范围。

### Work loop

```text
目标输入
  -> 主 Agent 理解与询问
  -> 自主编排专家和工具
  -> 生成简单回答或正式成果
  -> 根据风险规则自动推进或请求人工确认
  -> 进入内容、发布准备或其他执行模块
  -> 回收真实平台数据
  -> Agent 形成复盘与下一轮任务
```

### Cross-client batch

跨客户任务必须由用户明确多选后创建：

- 每个客户生成独立子任务和上下文。
- 每个客户独立审批和成果。
- 全局只汇总执行状态，不比较业务内容与数据。

## 4. System Surfaces

### App Shell

- 保留清晰全局导航。
- 客户 / 项目和账号上下文不与导航混在一起。
- 全局搜索与主 Agent 是两个不同入口。
- 通知和待办统一汇总。

### Brain

- 对话主体占据最大空间。
- 输入框固定底部。
- 专家接力、正式成果和确认面板嵌入对话。
- 不常驻右侧 Dashboard。
- 运行详情按需展开。

### Content

- 默认聚焦正文或脚本。
- 工具面板可开关。
- 正文宽度在任何面板组合下保持可读。
- 成果和发布包是类型化对象，而不是 JSON 或万能表单。

### Approval

- 队列用于效率。
- 预览用于判断。
- 风险和操作用于决策。
- 支持输入意见后驳回并重跑。

### Review

- 先结论，后证据。
- Agent 建议可以直接创建下一轮任务。
- 无数据时解释权限、同步和缺失原因，不渲染空图表。

## 5. Backend Evolution

优先复用现有模型和接口，增量补齐：

- `Client` 领域对象。
- `ProjectAccount` 多对多关系。
- 客户 / 项目成员授权。
- 正式成果库与版本。
- 用户 UI 偏好。
- 站内通知与待办。
- Agent 正式写入前的采用动作。

迁移要求：

- 现有组织映射到默认团队。
- 现有项目和账号迁移到默认客户，不丢失抖音 OAuth Token。
- 旧任务、内容和指标继续可读。
- API 变更先兼容旧前端调用，再在模块完成后清理旧接口。

## 6. Delivery Slices

### Slice 1: Design system and App Shell

- 新 token、字体、色彩、间距、圆角和状态规范。
- 客户 / 项目 / 平台 / 账号上下文骨架。
- 全局搜索、通知和 Agent 入口占位接口。
- 乱码修复、空状态和错误状态基础组件。

### Slice 2: Brain

- 新对话页面和流式 runtime。
- 普通问候与正式目标分流。
- 编辑部专家身份与强表现动效。
- 正式成果、确认面板、执行详情。

### Slice 3: Account matrix

- 客户账号资产与项目关联。
- 四视图、偏好记忆和批量操作。
- 真实 OAuth、同步、权限和风险状态。

### Slice 4: Content

- 自适应内容工作区。
- 类型化内容编辑器。
- 素材、版本、阶段、Agent 和发布包面板。

### Slice 5: Approval

- 三段式审批台。
- 风险分级规则。
- 允许、驳回并重跑、修改意见和审计。

### Slice 6: Review

- 目标与真实指标绑定。
- 数据叙事、归因、建议和下一轮任务。

### Slice 7: Remaining modules

- 专家团与独立调用。
- 知识库建议沉淀。
- 两层成本视图。
- 用户、专家和模型管理中心。

### Slice 8: Mobile key flows

- 对话、审批、通知、风险和账号状态。

## 7. Acceptance Gate Per Slice

每个 Slice 必须满足：

1. 高保真视觉稿已由用户明确批准。
2. 前后端代码完成。
3. 真实数据和关键操作可用。
4. 权限、空状态、错误状态和边界状态已验证。
5. 单元 / 接口测试通过。
6. localhost 桌面和移动端已验收。
7. 用户明确同意后才部署线上。
8. 线上冒烟测试通过并有回滚方式。

## 8. Non-goals

- 不在此次重构中开发投流。
- 不同时开发深色主题。
- 不建设客户门户和新手引导。
- 不使用 Mock 填满生产页面。
- 不在未获官方权限时实现自动发布。

## 9. First Review Target

下一步只进入 **Slice 1：设计系统与 App Shell 高保真方案**。

在该视觉稿批准前，不修改业务页面实现，也不部署生产环境。
