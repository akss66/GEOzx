# 运营大脑 V3 设计

> 日期：2026-07-30
> 基线：运营大脑 V2、生产整改增量及用户线上验收反馈
> 状态：已确认并进入实现

## 1. 目标

运营者只与主 Agent 对话，并能从账号运营的任意环节进入。主 Agent 负责理解目标、选择能力、监督执行、处理异常和交付结果；正式专业成果由对应专家产生；确定性读写由 Tool 完成；Runtime 负责状态、审批、幂等、重试、审计与隔离。

V3 必须同时改善两类体验：

- 普通交流和明确查询快速开始流式回答，不能在回答前串行等待一次重型意图模型。
- 复杂运营任务仍具备专家、证据、成果、审批和可恢复执行能力，不能用提速为理由绕过专业边界。

## 2. 架构

```text
用户
  -> 主 Agent 网关
     -> 作用域与待处理状态检查
     -> 确定性路由
        -> 普通对话：直接流式回答
        -> 数据查询：只读 Tool + 业务解释
        -> 明确 Skill：Skill Runtime
        -> 外部动作：审批门 + Tool
        -> 仍有歧义：轻量路由模型
     -> Skill Runtime
        -> 专家 Agent（可并行）
        -> Tool
        -> 按需质量门
        -> 唯一正式成果
     -> 主 Agent 汇总和下一步建议
```

主 Agent 始终拥有用户对话控制权。专家以 Agent-as-Tool 方式运行，默认不接管对话。只有明确需要专家持续直接交互的未来场景才允许 handoff。

## 3. 路由规则

路由顺序固定：

1. 校验 `org_id + user_id + account_id + thread_id + turn_id + run_id`。
2. 若存在待审批、待澄清或可恢复 SkillRun，按持久化状态确定下一步。
3. 若用户从能力菜单明确选择 Skill，零模型调用直接路由。
4. 对问候、能力询问、身份询问等明确普通交流，零路由模型调用进入回答模型。
5. 对明确只读数据查询，零路由模型调用进入查询 Tool。
6. 对明确且已发布的自然语言 Skill 请求，零路由模型调用进入 Skill Runtime。
7. 其余请求使用轻量路由模型；复杂答案、专家成果与最终综合仍使用强模型。

确定性路由只能在高置信度规则命中时生效。否定词和范围限制必须随本 Turn 保留，例如“不生成30天策略”“只查询”“不发布”。

## 4. Runtime 边界

- 每条用户消息只拥有一个 ConversationTurn 和一个当前 AgentRun。
- 重试复用同一业务幂等键，不重复写用户可见消息、成果或外部动作。
- 参数冲突、权限不足、缺少账号、未绑定项目和审批拒绝属于业务终态，不进入基础设施重试。
- 网络超时、限流和临时供应商故障允许有界重试。
- SkillRun、AgentRun、BrainTask 和 Turn 必须在同一收口步骤进入一致终态。
- 专家不能读取其他账号、其他会话或其他 Turn 的未显式引用数据。
- 正式成果必须带 `account_id + thread_id + turn_id + run_id + skill_run_id` 来源。

## 5. 专家与质量门

- `account_inspection`：定位、内容、运营专家组合。
- `topic_planning`、`script_generation`：内容策略/编导专家。
- `publishing_preparation`、`performance_review`：运营专家。
- 互不依赖的专家允许并行执行。
- 普通聊天和只读查询不运行 Critic。
- 正式报告、脚本、发布包等成果按 Skill 策略运行 Critic；最多进行有界改进，失败后给出可操作状态，不无限循环。
- 主 Agent 可以解释专家结论，但不得在专家没有成功执行时冒充专家产出正式成果。

## 6. 前端投影

- 对话只使用 ConversationTurn 作为唯一消息数据源，不再并存 Task 消息 UI。
- 用户提交后立即在与历史消息相同的 Turn 容器中显示本轮消息和运行状态。
- 状态文案只保留一个，例如“正在分析…”，不同时出现“思考中”和“正在思考”。
- 流式事件以 `thread_id + turn_id + client_message_id` 归并。
- 正式成果同时展示在来源 Turn 下方和成果中心，两处引用同一 Artifact。
- 默认展示业务阶段、参与专家、依据、结论和下一步；技术日志折叠后显示路由、模型、工具、质量门、重试和耗时。

## 7. 性能目标

- 确定性路由耗时：服务端 P95 小于 50 ms。
- 明确普通交流：只发生一次回答模型调用。
- 明确菜单 Skill：路由模型调用次数为 0。
- 明确只读查询：路由模型调用次数为 0。
- 普通交流首个流式文本：在模型供应商正常时 P95 小于 3 秒。
- 所有 Turn 技术日志能够分解路由、首字、完成和总耗时。

## 8. 验收

至少覆盖：

1. “你好，你叫什么”直接回答，只调用一次回答模型。
2. “你能做什么”直接回答，不执行专家或 Tool。
3. “查看最近30天播放和互动，只查询”直接查询，不创建策略。
4. 点击“一键账号体检”直接进入 Skill，不调用意图模型。
5. “账号体检，不生成30天策略”只产生体检成果。
6. “准备发布包，不实际发布”停在审批前，不产生外部发布。
7. 业务冲突不重试；临时供应商故障按策略有界重试。
8. 切换账号后聊天、成果、运行日志完全隔离。
9. 新消息从提交开始与历史 Turn 对齐，回答实时流式追加。
10. 技术日志能够说明参与专家和各阶段耗时。
