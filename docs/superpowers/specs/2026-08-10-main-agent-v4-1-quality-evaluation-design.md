# 运营大脑 V4.1：账号分析质量评测基线设计

## 1. 文档状态

- 日期：2026-08-10
- 状态：设计已获方向性批准，等待书面规格复核
- 当前实现分支：`codex/main-agent-v4-codex-interaction`
- 基线提交：`66e2c0f`
- 本规格只覆盖 V4.1 的第一个可独立交付切片：账号数据分析质量评测基线
- 本规格不改变当前生产运行时，不替换现有 LangGraph、SSE、WorkTurn 或专家执行链路

## 2. 背景与问题

运营大脑当前已经能够：

- 根据当前账号已确认导入的数据回答数据查询和账号分析问题；
- 调用账号分析 Skill、确定性数据工具、运营专家和质量审核；
- 在同一个 WorkTurn 中流式展示进度、正式回答、依据和技术记录；
- 按组织、用户、账号、会话和回合隔离数据与执行状态。

但现有自动化测试主要验证代码契约、接口状态和局部业务规则，尚未形成一套可持续回答以下问题的产品级评测体系：

1. 用户换一种说法后，主 Agent 是否仍能选择正确能力；
2. 回答里的数字、时间范围、单位和趋势方向是否与工具证据一致；
3. 数据不足时是否会明确收口，而不是编造诊断；
4. 用户要求“只分析现状”时，系统是否避免越权生成长期策略；
5. 专家、工具或质量审核异常时，系统是否安全降级并正确结束状态；
6. 不同账号、用户和会话之间是否始终保持严格隔离；
7. Prompt、模型或编排修改后，是否引入质量回退；
8. 端到端响应速度是否满足用户对实时 Agent 的预期。

V4.1 首先建立可重复、可比较、可进入 CI 的质量评测基线。没有评测基线前，不继续扩张自动发布、自动监测或更多专家能力。

## 3. 产品边界

当前正式产品边界保持不变：

> 主 Agent 只根据运营者已经确认导入的抖音数据，回答当前账号的数据问题并给出证据支持的运营建议。

本阶段明确不包含：

- 自动发布；
- 自动抓取抖音后台数据；
- 自动监测运营结果；
- 自动归因某条建议带来的业务提升；
- 自动修改账号策略；
- 对标账号视频采集和转写；
- Langfuse 生产部署；
- 用 AG-UI 重写现有实时交互协议；
- 用 assistant-ui 重写现有聊天页面。

上述能力可在评测基线稳定后分别设计和实施。

## 4. 方案选择

### 4.1 方案 A：只继续增加普通 Pytest

所有评测都写成现有单元测试和接口测试。

优点是没有新依赖、运行稳定；缺点是难以表达回答相关性、忠实度、多轮完整性和建议可执行性等语义质量，也不便形成统一的案例数据集和可比较报告。不单独采用。

### 4.2 方案 B：DeepEval + 确定性业务断言（采用）

保留 Pytest 作为执行入口和 CI 基础，新增独立评测案例集与统一结果模型：

- 确定性规则检查账号范围、路由、工具调用、数字、单位、时间范围、证据、禁用行为和终态；
- DeepEval 仅负责适合模型判断的任务完成度、回答相关性、忠实度、多轮完整性和角色遵循；
- 无模型密钥的 CI 只运行确定性门禁；
- 有评测模型的手动或受控流水线运行完整语义评测；
- 所有评测结果输出统一 JSON 报告，便于版本对比。

该方案与现有 Python、Pytest、LangGraph 和业务证据模型匹配，并且不会让第三方评测服务成为生产依赖。

### 4.3 方案 C：直接部署 Langfuse 或 Promptfoo 作为唯一评测平台

这类平台适合追踪、数据集管理、Prompt 对比和可视化报告，但无法代替本系统的账号隔离、数据口径、证据引用和运行终态等确定性业务校验。立即作为唯一基线会重复现有追踪设施，并增加基础设施复杂度。不采用。

后续可以为现有追踪模型增加可选 Langfuse exporter，但它不属于本规格。

## 5. 总体架构

```text
版本化评测案例集
    ↓
评测运行器
    ├─ 建立组织 / 用户 / 账号 / 数据 / Thread 测试场景
    ├─ 通过真实主 Agent API 或 Runtime 执行一轮或多轮对话
    ├─ 收集 Route / Tool / Skill / Expert / Critic / Evidence / Turn / Timing
    └─ 规范化为 EvaluationRecord
             ↓
    ┌────────┴────────┐
    │                 │
确定性业务门禁      可选 DeepEval 语义指标
    │                 │
    └────────┬────────┘
             ↓
      JSON 评测报告 + Pytest 结果
```

设计原则：

1. 生产系统仍是事实来源，评测层不得复制一套 Agent 业务实现；
2. 可用代码验证的事实不交给 LLM 判断；
3. LLM Judge 不参与生产请求，只运行在评测环境；
4. CI 不依赖外部模型、外部网络或生产数据；
5. 所有案例均具备稳定 ID、版本、场景输入和明确期望；
6. 一次 Prompt、模型或编排变更前后必须能比较同一批案例；
7. 评测失败只报告问题，不自动修改 Prompt 或生产配置。

## 6. 评测层边界

### 6.1 案例集

第一版建立 30 个真实运营者语句，分为六组，每组 5 个：

1. 数据存在性与数据范围；
2. 指标趋势、变化和作品表现；
3. 数据不足、数据过期和待确认批次；
4. 账号体检、现状分析和短周期建议；
5. 指令边界、连续追问和运行中补充限制；
6. 失败降级、幂等恢复和跨账号隔离。

每个案例至少声明：

```python
class EvaluationCase(BaseModel):
    case_id: str
    version: str
    category: str
    description: str
    account_fixture: str
    messages: list[str]
    expected_route: str | None
    expected_tools: list[str]
    forbidden_tools: list[str]
    expected_answerability: str | None
    required_claims: list[str]
    forbidden_claims: list[str]
    required_evidence_metrics: list[str]
    maximum_expert_invocations: int | None
    latency_budget_ms: int | None
```

案例文本与期望结果必须是代码库中的版本化文件，禁止只保存在个人表格、聊天记录或第三方平台。

### 6.2 运行器

运行器支持两种模式：

- `deterministic`：使用固定测试数据和可控模型替身，运行全部确定性门禁，作为 CI 必跑项；
- `live-model`：使用配置的真实模型执行相同案例，并追加 DeepEval 语义指标，只允许显式启动。

两种模式必须复用相同案例、业务入口和结果模型。禁止维护两套互相漂移的测试语料。

### 6.3 统一评测记录

每个案例生成一条规范化记录：

```python
class EvaluationRecord(BaseModel):
    case_id: str
    case_version: str
    mode: str
    started_at: datetime
    duration_ms: int
    route: str | None
    tool_calls: list[dict]
    skill_runs: list[dict]
    expert_invocations: list[dict]
    evidence_refs: list[dict]
    final_answer: str
    terminal_states: dict[str, str]
    deterministic_checks: list[dict]
    semantic_scores: dict[str, float]
    passed: bool
    failure_reasons: list[str]
```

报告默认写入被 Git 忽略的评测输出目录，不提交真实运行输出。代码库只提交案例、规则、基线摘要和必要的脱敏样例。

## 7. 确定性质量门禁

以下检查属于 P0，必须由代码完成，不能交给 LLM Judge：

### 7.1 范围与隔离

- 回答、证据和调用记录只属于当前 `org_id + user_id + account_id + thread_id + turn_id`；
- 切换账号后不得出现前一账号的文本、指标、证据或任务状态；
- 普通用户不能读取或删除其他用户的会话与执行记录。

### 7.2 路由与调用

- 简单数据存在性查询不得启动完整账号体检；
- 数据分析问题应进入账号数据分析能力；
- 用户明确要求一键体检时才进入完整体检 Skill；
- 用户明确禁止长期策略时，不得生成 30 天策略或写入策略记录；
- 未绑定项目但已选择合法账号时，账号级分析不得因项目范围校验失败；
- 业务冲突、权限错误和校验错误不得按临时故障重复重试。

### 7.3 事实与证据

- 回答中的数值、单位、时间范围、变化方向和作品排名必须在工具结果中找到对应事实；
- 每条关键结论至少有一条当前账号证据；
- 待确认批次不得参与正式分析；
- 没有对比周期时不得声称“上涨”或“下降”；
- 相关性不得表述为已经证实的因果关系；
- 数据为空时不得声称已经读取到可分析指标。

### 7.4 建议边界

- 建议必须包含动作、原因、验证指标和观察周期；
- 数据不足时不得给出伪精确提升比例；
- 用户只问事实时，回答应先直接给出事实，不得强制扩张为完整策略；
- 专家失败时应保留已验证的确定性事实，并清楚说明未完成部分；
- Critic 失败不得产生空白回答或虚假的“已完成”。

### 7.5 幂等与终态

- 同一 `client_message_id` 不得产生重复用户消息、重复正式回答或重复交付物；
- 重试必须复用同一 WorkTurn 身份；
- Turn、AgentRun、SkillRun 和必要的专家调用最终状态必须一致；
- 页面刷新或 SSE 重连不得重新执行已经完成的工具或专家步骤。

## 8. DeepEval 语义指标

DeepEval 只在 `live-model` 模式运行以下首批指标：

1. `Task Completion`：是否真正回答了用户问题；
2. `Answer Relevancy`：回答是否聚焦当前请求；
3. `Faithfulness`：解释是否忠实于提供的工具事实和证据；
4. `Turn Faithfulness`：连续追问中是否继续遵守前文事实和限制；
5. `Role Adherence`：主 Agent 是否保持“选择能力、监督和汇总”的角色；
6. 自定义 G-Eval：建议是否具体、可执行、带验证指标和观察周期。

语义指标不得检查数值相等、账号归属、工具参数或权限边界。这些内容必须由确定性门禁负责。

初始阈值：

- 单项语义指标通过阈值：`0.80`；
- 单案例所有 P0 确定性门禁：`100%` 通过；
- 30 个案例的语义指标平均分：不低于 `0.85`；
- 任何跨账号泄露、无证据数字或越权执行均直接判定整个评测批次失败。

阈值建立后只能通过评测配置版本变更调整，禁止为让某次提交通过而临时降低。

## 9. 性能评测

性能数据从现有 WorkTurn 和 LLM 调用追踪中读取，不新增第二套计时来源。

第一版记录：

- 用户请求到第一条业务状态；
- 用户请求到确定性数据事实可用；
- 用户请求到首段模型文本；
- 用户请求到最终回答；
- Tool、Expert、Critic 各阶段耗时；
- 模型队列、首 Token 和完整响应耗时；
- SSE 重连次数和恢复耗时。

目标基线：

- 第一条可见业务状态 P95 小于 1 秒；
- 简单数据存在性查询 P95 小于 2 秒；
- 账号数据事实 P95 小于 10 秒；
- 完整账号分析最终回答 P95 小于 45 秒；
- 有真实进展时，业务状态更新间隔不超过 3 秒。

首个版本的性能门禁默认只生成报告，不因共享测试环境抖动阻断 CI。确定稳定基线后再单独启用阻断阈值。

## 10. 安全、隐私与成本

- CI 案例只使用合成或脱敏数据；
- 不将生产账号原始数据、用户消息或模型密钥提交到仓库；
- `live-model` 必须显式配置评测模型和调用预算；
- 评测输出不得记录明文密钥、Authorization Header 或完整环境变量；
- DeepEval 自动加载 `.env` 的行为必须在测试入口中显式禁用，评测配置只读取项目允许的环境变量；
- 语义评测记录模型、Prompt 版本、Token 和费用，避免质量比较忽略成本变化；
- 外部观测和评测服务默认关闭。

## 11. 开源项目采用决策

### 本阶段直接采用

- DeepEval：作为可选评测依赖和语义指标实现；
- Pytest：继续作为本地和 CI 的统一执行入口。

### 本阶段只借鉴，不引入

- AG-UI：借鉴事件语义，现有 SSE 与持久事件保持不变；
- StaffDeck：借鉴执行记录、人工接管和持续反馈理念，不复制 AGPL 代码；
- Langfuse：预留可选 exporter，不成为本阶段依赖；
- assistant-ui：不替换现有业务化 WorkTurn UI；
- douyin-creator-toolkit：后续独立评估竞品转写和内容拆解能力，不进入当前账号数据分析主链路；
- Postiz：自动发布和内容日历不属于当前产品边界。

## 12. 测试策略

实现过程严格采用失败测试、最小实现、回归验证：

1. 案例 Schema 和加载校验单元测试；
2. 确定性门禁逐项单元测试；
3. EvaluationRecord 规范化和报告序列化测试；
4. 固定模型替身下的 30 案例 CI 测试；
5. DeepEval 适配器在未安装、未配置和正常配置时的测试；
6. 真实模型评测命令的预算、超时和错误收口测试；
7. 一次完整本地确定性评测；
8. 一次显式启动的真实模型基线运行；
9. 对基线失败分类，不为通过评测而隐藏失败样本。

## 13. 验收标准

V4.1 第一阶段完成必须同时满足：

- 30 个版本化案例均能被严格加载和校验；
- 无模型密钥时确定性评测可在 CI 稳定运行；
- P0 确定性门禁全部通过；
- DeepEval 未安装或未配置时，不影响生产应用和普通测试；
- 显式启用后能输出六类语义分数及解释；
- 报告包含案例版本、代码提交、Prompt 版本、模型、耗时、成本和失败原因；
- 评测输出不包含跨账号内容或密钥；
- 现有后端测试、前端测试、静态检查和生产构建继续通过；
- 不改变生产用户可见行为，不新增页面，不部署新基础设施；
- 评测基线结果可作为后续 Prompt、模型和编排修改的合并门禁依据。

## 14. 后续阶段

完成本规格并取得稳定基线后，按独立规格推进：

1. 依据失败样本整改主 Agent 路由、证据校验、降级回答和性能瓶颈；
2. 增加可选 Langfuse/OpenTelemetry exporter，形成生产反馈到评测案例的闭环；
3. 让现有事件模型逐步兼容 AG-UI 语义，但不破坏现有客户端；
4. 建设独立的对标内容实验室，评估视频转写、竞品结构拆解和模式复用；
5. 在数据来源和评测体系成熟后，再讨论自动发布、自动监测和效果归因。
