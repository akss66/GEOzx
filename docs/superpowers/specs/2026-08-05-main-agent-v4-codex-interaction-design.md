# 运营大脑 V4 Codex 式交互收口设计

## 1. 文档状态

- 日期：2026-08-05
- 状态：产品方向已确认，等待产品负责人审阅本文
- 适用范围：运营大脑主对话、账号数据诊断、专家分析、实时进度、用户补充要求、停止、异常恢复与最终运营建议
- 当前产品边界：只根据运营者已经导入的数据判断账号当前状态并给出建议；不负责自动发布、自动监测、效果归因或自动调整策略
- 上游约束：不同账号的数据、会话、运行状态和诊断报告必须严格隔离

## 2. 目标

将运营大脑主界面统一为接近 Codex / Claude Code 的任务交互：

1. 用户发送消息后立即得到可见反馈。
2. 一条用户消息只创建一个持续更新的工作回合。
3. 当前工作、已完成步骤、等待用户事项和最终回答始终在原位置呈现。
4. 用户在运行过程中仍可补充要求、改变限制或停止工作。
5. 技术日志默认隐藏，用户看到的是可理解的业务过程。
6. 最终回答必须说明当前状态、数据依据、优先建议和数据限制。
7. 页面断线、刷新或短暂失败后可恢复同一工作回合，不创建重复消息。

成功标准不是动画数量，而是用户能否始终回答四个问题：

- 系统现在在做什么？
- 已经完成了什么？
- 是否需要我做决定？
- 最终交付了什么？

## 3. 方案选择

### 方案 A：只修补现有聊天 UI

保留现有消息、卡片和状态路径，仅调整头像、气泡、文案和加载动画。

优点是改动小；缺点是不能解决双渲染、重复消息、刷新后状态丢失、过程与最终回答分裂等根因。不采用。

### 方案 B：在现有运行时上统一单 WorkTurn 交互

保留现有 `ConversationThread`、`ConversationTurn`、`AgentRun`、`SkillRun`、SSE 和账号隔离，在前端增加统一的 WorkTurn 投影和语义化事件呈现。

优点是保留现有可靠性建设，同时得到 Codex 式交互；风险和迁移范围可控。采用本方案。

### 方案 C：整体替换为通用 Agent 聊天框架

使用通用聊天 UI 和 Runtime 重写前后端交互。

优点是能快速获得通用流式组件；缺点是会重复建设账号上下文、专家执行、数据诊断和历史归属，并容易再次形成新旧两套 UI。不采用。

## 4. 核心交互模型

```text
ConversationThread
  └─ WorkTurn
       ├─ user_message
       ├─ agent_commentary
       ├─ progress_step
       ├─ data_inspection
       ├─ expert_analysis
       ├─ user_decision
       ├─ final_answer
       └─ technical_trace
```

### 4.1 Thread

Thread 是一个账号下的长期会话。每个 Thread 固定关联组织、用户和账号。切换账号必须切换或新建 Thread，不能在原 Thread 覆盖账号上下文。

### 4.2 WorkTurn

每条用户消息创建一个 WorkTurn。理解需求、检查数据、调用专家、整理建议、等待补充、异常恢复和最终回答都在同一 WorkTurn 中原位更新。

用户可见状态：

```text
received
working
waiting_user
completed
interrupted
failed
```

前端不得把临时消息和历史消息使用不同容器，也不得在完成后把消息移动到另一套渲染路径。

### 4.3 Item

Item 是 WorkTurn 内部的语义化工作单元。Item 拥有稳定 ID、开始状态、增量更新和最终状态。完成事件是权威状态。

V4 当前只需要以下用户侧 Item：

| Item | 用户看到的内容 |
|---|---|
| `agent_commentary` | 简短、真实的工作更新 |
| `progress_step` | 读取数据、检查完整度、专家分析、整理建议 |
| `data_inspection` | 使用的数据周期、来源、完整度和缺口 |
| `expert_analysis` | 专家名称和结论摘要，默认折叠 |
| `user_decision` | 缺少关键数据或存在方向分歧时的选择 |
| `final_answer` | 当前状态、依据、建议、限制 |
| `technical_trace` | Run、Skill、Tool、模型、耗时、重试，默认深度折叠 |

## 5. 页面结构

```text
┌──────────────────────────────────────────────┐
│ 当前账号：阿K桑                   数据截至 07/31 │
├──────────────────────────────────────────────┤
│                                              │
│ 用户                                   帮我分析账号 │
│                                              │
│ 运营大脑 · 正在分析                           │
│ ◉ 正在检查近30天播放、互动和粉丝变化……          │
│                                              │
│ ✓ 已读取账号数据                               │
│ ✓ 已检查数据完整度                             │
│ ◌ 正在分析主要问题                             │
│ ○ 正在整理运营建议                             │
│                                              │
│ ▸ 查看分析过程                                 │
│                                              │
│ [完成后在同一位置展示最终回答]                   │
│                                              │
├──────────────────────────────────────────────┤
│ ＋ 继续补充要求……                       ■ 停止 │
└──────────────────────────────────────────────┘
```

页面只保留四个主区域：账号上下文、统一对话流、当前 WorkTurn、固定输入框。专家详情和技术日志是辅助披露，不得抢占主对话。

## 6. 过程呈现

### 6.1 即时反馈

消息提交成功后立即渲染用户消息和空的主 Agent WorkTurn，不等待模型或 Worker 返回完整结果。

首个状态必须具体，例如：

- 正在确认本次问题需要读取哪些账号数据；
- 正在核对最近导入的数据周期；
- 正在比较播放、互动和粉丝变化；
- 正在整理优先建议和数据限制。

禁止重复显示“思考中”和“正在思考”。头像呼吸态只作为运行中的视觉提示，文字状态只有一处。

### 6.2 Commentary 与 Final

`agent_commentary` 用于一至两句简短过程沟通，不输出模型原始思维链，不把每次 Tool 调用变成聊天气泡。

`final_answer` 是正式交付，结构固定为：

1. 数据情况；
2. 当前账号状态；
3. 主要问题与机会；
4. 数据依据；
5. 优先建议；
6. 数据限制与可信度。

最终回答在原 WorkTurn 中出现，替代运行态主体，不追加第二个运营大脑气泡。

### 6.3 逐层披露

默认层只显示业务进度和最终回答。

第一层“查看分析过程”显示：使用的数据、专家、阶段结论和质量检查摘要。

第二层“技术详情”显示：Run/Skill/Tool ID、模型、耗时、重试、错误分类和 Trace。普通用户默认不展开。

## 7. 运行中交互

### 7.1 补充当前要求

运行时输入框保持可用。新消息默认由主 Agent判断为：

- 加入当前 WorkTurn 的新限制；
- 替换当前分析重点；
- 停止当前工作；
- 排队成为下一 WorkTurn。

前端必须显示判断结果，例如：

> 已加入当前分析：只判断账号现状，不生成长期策略。

用户可以撤销本次判断。

### 7.2 停止

运行中发送按钮切换为停止按钮，同时仍允许输入补充要求。停止后 WorkTurn 进入 `interrupted`，保留用户消息、已完成步骤和数据检查结果。

### 7.3 等待用户

只有缺少会改变结论的关键数据，或用户要求存在明显方向分歧时才暂停。

暂停卡必须使用业务语言，例如：

> 当前缺少单作品完播率。可以继续分析流量与粉丝趋势，但不能准确判断内容留存问题。

操作：`继续使用现有数据`、`前往补充数据`。

## 8. 异常与恢复

1. SSE 断开时保持当前快照，自动使用 `Last-Event-ID` 或 sequence 补齐事件。
2. 页面刷新后先读取 WorkTurn 快照，再订阅后续事件。
3. 前端按 `(turn_id, item_id, sequence)` 幂等归并。
4. 重试复用原 Turn、Run、SkillRun 和 Item 身份。
5. 专家失败时保留已完成的数据检查，只重试未完成部分。
6. 不可恢复失败必须关闭 Turn 和 Run，并给出可操作的恢复按钮。

失败示例：

```text
运营大脑 · 本次分析未完成

已完成
✓ 数据范围检查
✓ 指标完整度检查

尚未完成
- 专业诊断
- 运营建议

[重试未完成部分]
```

## 9. 前端状态边界

服务端数据库是 Turn、Run、SkillRun 和 Item 最终状态的事实来源。前端只维护：

- 乐观插入的用户消息；
- 当前连接状态；
- 尚未持久化的流式文本；
- 折叠状态；
- 输入草稿和排队消息。

禁止由多个组件分别推导同一 Turn 状态。统一 WorkTurn selector 产生唯一 ViewModel，历史和当前运行中的 Turn 使用同一组件树。

## 10. 账号隔离

所有快照、事件、重连、停止、补充消息和技术详情查询必须同时校验：

```text
org_id + user_id + account_id + thread_id + turn_id
```

切换账号时立即取消旧 SSE、清理当前草稿和临时运行投影，再加载新账号 Thread。不得短暂显示上一个账号的消息或结果。

## 11. 验收标准

### 11.1 功能

- 一条用户消息只产生一个用户消息节点和一个主 Agent WorkTurn。
- 用户消息从提交到完成始终保持同一位置、宽度和组件。
- 运行状态、Commentary 和 Final 在同一 WorkTurn 原位切换。
- 运行中可补充要求和停止。
- 专家和技术过程默认折叠。
- 页面刷新和断线后无需手工刷新即可恢复。
- 不同账号之间不存在消息、事件、草稿或结果串线。

### 11.2 性能

- 用户消息乐观显示：100ms 内；
- 首个明确工作状态：P95 小于 500ms；
- 普通回答首段流式内容：P95 小于 2 秒，不包含模型排队时间时单独统计；
- 有真实进展时，长分析状态更新间隔不超过 3 秒；
- 断线重连并恢复当前 Turn：P95 小于 2 秒。

### 11.3 一致性

- 重复用户消息：0；
- 重复主 Agent最终回答：0；
- Turn 与 AgentRun 终态不一致：0；
- 回答完成后布局跳动或重新对齐：0；
- 未导入数据却声称已读取：0；
- 缺少证据却输出确定性专业结论：0。

## 12. 测试策略

### 12.1 单元测试

- WorkTurn ViewModel 投影；
- Item started/delta/completed 幂等归并；
- Commentary、Final 和错误状态切换；
- 补充、排队、停止分类；
- 账号切换时状态清理。

### 12.2 合约测试

- REST 提交消息与 SSE 事件身份一致；
- 快照加增量事件可还原相同 WorkTurn；
- 重试不创建第二份消息或最终回答；
- 所有事件包含完整账号与会话范围。

### 12.3 浏览器测试

- 乐观消息与历史消息从开始到结束保持对齐；
- 真实流式输出可见；
- 呼吸态与单一状态文字不重复；
- 运行中追加限制后只更新受影响步骤；
- 停止、刷新、重连后状态正确；
- 失败只重试未完成部分；
- 切换账号不出现上一账号内容。

### 12.4 真实账号冒烟

至少覆盖：普通问答、查询已有数据、账号诊断、数据不足、专家失败、运行中补充限制、停止、刷新恢复和账号切换。

## 13. 非目标

本轮不实现：

- 自动发布；
- 自动监测抖音数据；
- 运营成效归因；
- 自动学习和自动调整策略；
- 通用开放式多 Agent 工作台；
- 重新设计账号数据中心；
- 整体替换现有前端技术栈。
