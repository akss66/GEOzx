# 账号数据中心批量摄取与增量合并设计

> 日期：2026-07-31
> 状态：已完成产品方向确认，待用户审阅书面规格
> 范围：账号数据中心的多文件导入、解析识别、增量合并、来源追溯、撤销重建与操作界面

## 1. 背景与问题

账号数据不是由一份表格一次性构成，而是由多个时间段、多个数据类型、多个来源的表格持续累积而成。运营者可能一次拖入多份文件，也可能在若干天后再次导入一个与历史周期部分重叠的新文件。

当前实现仍以“单文件批次”为页面主状态，导致以下问题：

1. 上传一份表后，界面会把某个数据域的 `available` 解释为“数据完整”。
2. 只要当前存在批次，上传入口就显示“更换文件”，没有区分待确认文件和已经写入的历史批次。
3. 前后端接口一次只接收一个文件，不能统一展示多文件识别和写入结果。
4. 模板识别要求列数和列顺序完全一致，无法稳健处理额外列、列顺序变化或一个工作簿中的多个工作表。
5. 账号、作品、粉丝和周期快照的唯一约束包含 `import_batch_id`。同一业务日期在后续批次中再次出现时，会产生另一条批次记录，而不是真正的规范化更新。
6. 当前统一查询层只对部分作品指标进行展示时合并；账号趋势、粉丝画像和周期数据仍可能保留重叠快照，直接读取这些表的消费者存在重复统计风险。
7. 某些投影代码会把新文件未提供的字段写成 `0` 或 `NULL`，不能保证“缺失字段保留旧值，明确的零才覆盖旧值”。
8. 现有撤销保护主要检查作品身份归属，尚未覆盖字段级更新之后的恢复语义。

因此，本次整改不是增加一个多选文件框，而是把导入链路改造成“原始数据账本 + 字段级观察值 + 规范化当前视图”的增量数据管道。

## 2. 已确认的产品规则

1. 用户可以一次拖入多份 Excel 或 CSV 文件。
2. 系统自动识别每个文件及工作表的数据类型。
3. 识别成功且校验通过的数据直接写入，不再要求逐文件点击确认。
4. 一个文件失败不能阻塞同一批操作中的其他有效文件。
5. 失败文件必须保留明确原因，可单独重试。
6. 重叠周期按业务主键和字段进行增量合并。
7. 新文件未提供的字段不得清空旧值。
8. 明确的数值 `0` 是有效数据，必须能够更新旧值。
9. 每个规范化字段必须能够追溯到文件、工作表、原始行、导入批次和确认时间。
10. 撤销或永久删除旧批次时，不得误删后来导入的数据。
11. 数据概览不得再声称“完整”或使用固定的 `1/4` 完成度。
12. 完成一轮导入后，主操作是“继续导入更多文件”，不是“更换文件”。

## 3. 设计目标

### 3.1 功能目标

- 批量上传、批量识别、文件级隔离处理。
- 支持一个 XLSX 内多个可识别工作表。
- 对重叠日期和重叠作品执行字段级更新。
- 保留原始文件和全部来源证据。
- 为每次导入提供新增、更新、未变化、失败统计。
- 支持安全撤销、永久删除和重试。
- 所有数据继续严格按组织和账号隔离。

### 3.2 非目标

- 本次不接入新的第三方数据供应商。
- 本次不实现任意未知表格的模型推断映射。
- 本次不允许模型在无法确定模板或业务主键时自动猜测。
- 本次不删除现有导入历史和原始文件。
- 本次不改变抖音官方 API 的来源优先级。

## 4. 方案选择

### 4.1 方案 A：前端循环调用现有单文件接口

优点是开发量小。缺点是底层仍按批次产生重叠快照，不能解决重复统计、字段覆盖和撤销恢复问题。

结论：不采用。

### 4.2 方案 B：直接覆盖现有快照行

优点是查询简单。缺点是覆盖后无法可靠恢复旧值，来源字段可能来自多个文件，单个 `import_batch_id` 无法表达字段级来源。

结论：不采用。

### 4.3 方案 C：原始导入账本 + 字段观察值 + 规范化当前值

每次导入保留不可变原始证据；每个明确提供的字段产生一条可追溯观察值；系统依据来源优先级和确认时间选择胜出观察值，并物化为账号当前可用数据。

优点：

- 缺失字段不会覆盖旧值。
- 明确的零值可以更新。
- 可精确计算新增、更新和未变化。
- 撤销批次后可以从剩余观察值重建。
- 同一字段的历史值、来源和变更过程完整可查。

结论：采用方案 C。

## 5. 总体架构

```text
用户拖入多个文件
       |
       v
批量导入任务 ImportJob
       |
       +-- ImportFile A -- 工作表 1 -- 数据集/批次 A1
       |                \- 工作表 2 -- 数据集/批次 A2
       |
       +-- ImportFile B -- 数据集/批次 B1
       |
       \-- ImportFile C -- 解析失败（不影响 A、B）
                            |
                            v
原始文件 + 原始行账本
                            |
                            v
字段观察值 FieldObservation
                            |
                            v
确定性胜出规则 / 重建器
                            |
                            v
规范化账号当前数据 Canonical Projection
                            |
                            v
运营大脑、运营复盘、账号数据概览
```

## 6. 数据模型

### 6.1 批量导入任务

新增 `data_import_jobs`：

- `id`
- `org_id`
- `account_id`
- `created_by_id`
- `client_request_id`
- `status`: `processing | completed | completed_with_errors | failed`
- `file_count`
- `recognized_dataset_count`
- `committed_dataset_count`
- `failed_file_count`
- `created_at`
- `completed_at`

唯一约束：

```text
(org_id, account_id, client_request_id)
```

用于防止浏览器重试或网络重放导致重复导入。

### 6.2 上传文件

新增 `data_import_files`：

- `id`
- `job_id`
- `org_id`
- `account_id`
- `filename`
- `content_type`
- `byte_size`
- `sha256`
- `storage_key`
- `status`: `uploaded | parsing | recognized | committed | needs_attention | failed | duplicate`
- `error_code`
- `error_message`
- `parser_version`

原始文件只保存一次。一个文件可以产生多个工作表数据集。

### 6.3 数据集与现有批次

沿用 `data_import_batches` 作为一个可独立提交的数据集，新增：

- `job_id`
- `import_file_id`
- `worksheet_name`
- `detected_template_code`
- `auto_committed_at`

一个 CSV 对应一个数据集；一个 XLSX 中每个已识别工作表对应一个数据集。

现有单文件导入批次允许上述字段为空，保证兼容。

### 6.4 字段观察值

新增 `data_field_observations`，保存规范化字段的不可变版本：

- `id`
- `org_id`
- `account_id`
- `batch_id`
- `import_file_id`
- `row_number`
- `worksheet_name`
- `entity_type`
- `entity_key`
- `observed_start`
- `observed_end`
- `field_name`
- `value_json`
- `source_kind`
- `source_priority`
- `confirmed_at`
- `is_active`

唯一约束：

```text
(batch_id, row_number, entity_type, entity_key, field_name)
```

未在文件中出现的字段不产生观察值。空白单元格默认不产生观察值；明确的 `0`、`0%` 和空字符串型合法值必须与缺失值区分。

### 6.5 规范化当前值

现有快照表逐步转为规范化投影，唯一键不再包含 `import_batch_id`：

#### 账号趋势

```text
(org_id, account_id, stat_date)
```

#### 作品指标

```text
(org_id, account_id, platform_content_record_id, stat_date)
```

作品身份无法稳定确定时不得自动写入规范化层，文件进入 `needs_attention`。

#### 粉丝画像

```text
(org_id, account_id, stat_date, dimension)
```

#### 周期聚合

```text
(org_id, account_id, period_start, period_end, content_format, vertical, metric_code)
```

每个规范化行增加 `field_provenance` JSON，记录各字段当前胜出观察值 ID、批次、文件和时间。单一 `import_batch_id` 不再承担整行来源含义。

## 7. 模板识别与解析器

### 7.1 多文件与多工作表

- 前端一次提交 `files[]`。
- 后端限制单文件大小、总大小、文件数量和总行数。
- XLSX 逐工作表扫描。
- 空白工作表和明确的说明页跳过并记录原因。
- 每个非空工作表独立识别模板。
- 同一个工作簿内部分工作表失败时，其他已识别工作表仍可提交。

### 7.2 表头匹配

模板识别从“列数、列顺序完全一致”改为：

1. 对表头执行 BOM、空格、全半角和已登记别名标准化。
2. 必填字段必须存在。
3. 列顺序可以变化。
4. 额外未知列允许存在，记录 `ignored_columns` 警告。
5. 重复标准化表头仍视为错误。
6. 多个模板同时匹配时，根据模板独有字段打分。
7. 最高分并列时标记 `ambiguous_template`，不得猜测写入。

### 7.3 安全边界

保留并扩展现有安全限制：

- XLSX ZIP 炸弹检测。
- 禁止宏、外部链接和公式。
- 限制压缩前后大小、文件数、工作表数、列数和总行数。
- 文件名清洗。
- 存储失败与数据库失败双向补偿。
- 不向前端暴露服务器路径或内部异常。

建议初始限制：

- 单次最多 20 个文件。
- 单文件最多 10 MB。
- 单次总大小最多 100 MB。
- 单工作表最多 10,000 行。
- 单次总行数最多 50,000 行。
- 同时解析最多 3 个文件，避免内存峰值。

## 8. 合并规则

### 8.1 业务主键

| 数据类型 | 业务主键 |
|---|---|
| 账号每日趋势 | 账号 + 日期 |
| 作品指标 | 账号 + 稳定作品身份 + 数据日期 |
| 粉丝画像 | 账号 + 日期 + 画像维度 |
| 周期聚合 | 账号 + 起止周期 + 体裁 + 垂类 + 指标 |

### 8.2 字段胜出规则

按以下顺序选择胜出观察值：

1. 来源优先级：官方 API > 平台导出 > 已验证截图 > 人工录入。
2. 同来源优先级下，确认时间较晚者优先。
3. 时间相同时，批次 ID 和观察值 ID 较大者优先，保证确定性。

### 8.3 缺失值与零值

- 字段不在模板中：不产生观察值。
- 单元格为空或缺失标记：默认不产生观察值。
- `0`、`0.0`、`0%`：产生观察值并允许覆盖。
- 当前版本不提供“通过空白单元格清除历史值”的能力。
- 将来如需清除，必须使用显式的人工操作和单独审计事件。

### 8.4 重叠周期示例

第一次导入：2026-07-01 至 2026-07-30。
第二次导入：2026-07-06 至 2026-08-04。

结果：

- 07-01 至 07-05 保留。
- 07-06 至 07-30 对新文件提供的字段进行更新。
- 07-31 至 08-04 新增。
- 新文件缺失的字段继续使用旧观察值。
- 值相同的字段计入“未变化”，但新来源仍写入观察值账本。

### 8.5 写入统计

每个数据集和整个任务返回：

- `inserted_entity_count`
- `updated_entity_count`
- `unchanged_entity_count`
- `inserted_field_count`
- `updated_field_count`
- `unchanged_field_count`
- `rejected_row_count`
- `warning_count`

## 9. 事务、并发与幂等

### 9.1 文件级隔离

- 一个文件或工作表数据集一个数据库事务。
- 该数据集任一阻塞错误发生时，整个数据集不写入规范化层。
- 同一任务中的其他文件继续处理。

### 9.2 并发

- 同一账号、同一规范化业务主键的重建使用 PostgreSQL 行锁或确定性 advisory lock。
- 锁顺序按业务主键排序，避免死锁。
- 写入前后均基于全部有效观察值重算胜出结果。

### 9.3 幂等

- 请求级：`client_request_id` 防止整个批量任务重放。
- 文件级：账号 + SHA-256 + 解析器版本识别完全相同的文件。
- 数据集级：文件 + 工作表 + 模板唯一。
- 观察值级：批次 + 行 + 实体 + 字段唯一。

完全相同文件再次上传时：

- 不重复创建观察值。
- 返回 `duplicate` 和原批次引用。
- 页面计入“未变化”，允许用户打开原导入记录。

内容发生变化但周期相同时：

- 创建新的来源批次和观察值。
- 重新计算受影响规范化字段。

## 10. 撤销、删除与重建

原始导入账本是事实来源，规范化表是可重建投影。

撤销或永久删除批次时：

1. 锁定该批次影响的所有规范化业务主键。
2. 将该批次的字段观察值标记为无效，或在永久删除时删除。
3. 对每个受影响字段从剩余有效观察值中重新选择胜出值。
4. 没有剩余观察值的字段恢复为空；整行没有字段时删除规范化行。
5. 后来批次的观察值不受影响。
6. 记录重建前后差异和操作人。

因此旧批次不再“拥有”规范化整行，也不会因为后来数据更新而出现无法安全撤销的死结。

## 11. API 设计

### 11.1 创建批量导入

```http
POST /account-data/{account_id}/import-jobs
Content-Type: multipart/form-data

client_request_id=<uuid>
files[]=daily.xlsx
files[]=works.xlsx
files[]=aggregate.csv
```

返回 `202 Accepted`：

```json
{
  "id": 91,
  "status": "processing",
  "file_count": 3,
  "files": [
    {"id": 301, "filename": "daily.xlsx", "status": "uploaded"},
    {"id": 302, "filename": "works.xlsx", "status": "uploaded"},
    {"id": 303, "filename": "aggregate.csv", "status": "uploaded"}
  ]
}
```

小批量任务可以在请求内完成，但接口契约始终返回 Job，前端不依赖同步处理时长。生产默认由 Worker 执行解析和提交。

### 11.2 查询任务

```http
GET /account-data/{account_id}/import-jobs/{job_id}
```

返回任务、文件、工作表、识别类型、周期、写入统计、警告和错误。

### 11.3 重试失败文件

```http
POST /account-data/{account_id}/import-jobs/{job_id}/files/{file_id}/retry
```

只允许失败或待处理文件重试，并使用新的解析尝试记录，不覆盖原失败证据。

### 11.4 兼容接口

现有 `POST /account-data/{account_id}/imports` 暂时保留，内部转为创建一个只包含单文件的 Job。前端新入口只调用批量接口。

### 12.1 空态

拖入账号数据文件
支持一次选择多份 Excel / CSV，系统会自动识别并合并

不展示“选择某一种模板”的前置步骤。

每个文件一行：

### 12.3 任务结果

顶部结果按任务汇总：

```text

成功 4 · 失败 1
新增 35 · 更新 248 · 未变化 612
```

失败文件提供：

- 查看原因
- 重新上传该文件
- 下载原文件

有效文件不需要再次确认。

### 12.4 完成后的操作

- 主按钮：“继续导入更多文件”
- 次按钮：“查看数据概览”
- 次按钮：“查看导入记录”

“更换当前文件”仅在文件仍处于本地选择、尚未提交服务器时出现。写入完成后不再出现。

### 12.5 数据概览

移除：

- “数据完整”
- “待补齐”
- 固定 `1/4` 或 `4/4`
- “补齐数据”

改为展示：

- 已拥有的数据来源类型
- 各来源覆盖周期
- 最近导入时间
- 文件/批次数
- 待处理冲突数

操作统一为：

- “继续导入”
- “查看来源”
- “交给运营大脑分析”

## 13. 错误处理

错误分为：

1. 文件级：扩展名、大小、文件损坏、危险 XLSX。
2. 工作表级：未知模板、歧义模板、缺少必填列。
3. 行级：无效日期、数值越界、作品身份冲突。
4. 写入级：并发冲突、数据库异常、存储异常。

处理原则：

- 一个失败文件不阻塞其他文件。
- 一个工作表存在阻塞行时，该工作表数据集不部分写入。
- 用户看到可操作的中文原因。
- 技术错误码和详细日志仅在展开区域或审计记录中展示。
- 所有失败都可以安全重试，重试不会重复写入成功文件。

## 14. 数据迁移

迁移必须分阶段：

### 阶段 1：新增结构

- 新增 Job、File、FieldObservation 表。
- 给批次增加可空关联字段。
- 给规范化表增加业务主键索引和 `field_provenance`。
- 旧读路径保持不变。

### 阶段 2：回填

- 从所有已提交、未撤销批次及其原始行生成字段观察值。
- 根据胜出规则生成规范化投影。
- 输出回填报告：批次数、观察值数、重叠键数、冲突数。

### 阶段 3：双读比对

- 新旧查询同时运行。
- 对账号周期、作品数量和关键指标进行差异记录。
- 不一致时继续使用旧读路径并阻止切换。

### 阶段 4：切换

- 账号数据中心、运营大脑工具和复盘服务统一读取规范化层。
- 确认稳定后再移除旧的批次唯一约束。

禁止在未完成回填和差异验证前直接修改生产唯一键。

## 15. 测试与验收

### 15.1 解析器

- 多文件混合 XLSX/CSV。
- 一个 XLSX 多工作表。
- 空白页、说明页、未知页。
- 列换序、额外列、别名列。
- 缺少必填列、重复列、歧义模板。
- 大文件、ZIP 炸弹、公式、宏、外链。

### 15.2 合并

- 完全不重叠周期。
- 部分重叠周期。
- 完全重叠但值变化。
- 完全重叠且值不变。
- 新文件字段缺失。
- 新文件字段明确为零。
- 同一作品来自作品列表和单作品分析表。
- 官方 API 与文件来源冲突。

### 15.3 撤销与删除

- 撤销最新批次恢复旧值。
- 撤销旧批次不影响新值。
- 永久删除原文件同步清理对应观察值。
- 删除失败时文件和数据库均恢复。
- 同一批次重复撤销/删除保持幂等。

### 15.4 并发与重试

- 同一任务请求重放。
- 相同文件重复上传。
- 两个用户同时导入同一账号同一周期。
- Worker 中途退出后恢复。
- 成功 4 个、失败 1 个后只重试失败文件。

### 15.5 前端

- 拖入多文件并显示独立状态。
- 成功文件自动写入。
- 失败文件不遮挡成功结果。
- 完成后显示“继续导入更多文件”。
- 不再出现“数据完整”“补齐数据”和已提交后的“更换文件”。
- 账号切换后任务和结果严格隔离。

## 16. 可观测性

记录以下指标：

- 导入任务数量和成功率。
- 文件识别成功率。
- 各模板解析耗时和行数。
- 新增、更新、未变化字段数量。
- 歧义模板和作品身份冲突数量。
- Worker 重试和恢复次数。
- 规范化重建耗时。
- 新旧读路径差异数量。

日志必须包含 `org_id`、`account_id`、`job_id`、`file_id`、`batch_id`，但不得记录原始敏感数据值。

## 17. 发布与回滚

1. 先部署新增表和兼容代码，不切换读路径。
2. 在生产副本上执行回填和差异报告。
3. 对指定管理员和账号启用批量导入。
4. 验证重叠周期、零值、缺失值和撤销。
5. 再切换运营大脑与复盘读取规范化层。
6. 保留旧读路径和 release 作为回滚目标，直到差异指标稳定。

回滚代码时保留新增账本和观察值，不执行破坏性数据库降级。

### 17.1 历史数据回填操作

数据库迁移完成后，先对单一账号演练：

```powershell
cd backend
.\.venv\Scripts\python.exe -m scripts.backfill_account_data_observations `
  --org-id <ORG_ID> --account-id <ACCOUNT_ID> --batch-size 100
```

确认无误后移除 `--account-id`，按组织逐账号执行。命令按批次提交并在
`account_data_backfill_checkpoints` 保存最后确认时间和批次 ID；中断后可执行同一命令，
已完成账号会直接返回零处理量。回填只读取已提交批次，撤销批次会记录为跳过。

上线前核对：

```sql
SELECT account_id, COUNT(*) AS observation_count
FROM data_field_observations
WHERE active = TRUE
GROUP BY account_id
ORDER BY account_id;

SELECT account_id, processed_batch_count, last_batch_id, completed_at
FROM account_data_backfill_checkpoints
ORDER BY account_id;

SELECT account_id, stat_date, COUNT(*) AS duplicate_count
FROM account_metric_snapshots
GROUP BY account_id, stat_date
HAVING COUNT(*) > 1;
```

回填期间读取继续兼容旧快照：有观察值时使用规范化来源与字段证据，没有观察值的账号仍读取
旧快照。回滚边界是应用 release，不删除观察值或 checkpoint；若出现差异，停止后续账号回填，
保留现场并切回上一 release。

## 18. 验收标准

以下条件全部满足才算完成：

1. 一次可拖入多份文件并自动识别。
2. 一个失败文件不影响其他文件写入。
3. 重叠日期按字段更新，非重叠日期保留。
4. 缺失字段不覆盖，明确零值能覆盖。
5. 同一文件重试不重复写入。
6. 每个规范化字段可追溯到原文件和原始行。
7. 撤销旧批次不破坏后来数据。
8. 所有账号级聊天、任务和导入结果继续按账号隔离。
9. 页面不再使用“数据完整”“补齐数据”和错误的“更换文件”语义。
10. 自动化测试、迁移验证、生产构建和浏览器验收全部通过。
