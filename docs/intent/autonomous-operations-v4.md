# 同舟行 · 自主运营系统 V4 意图基线

## 文档状态

- 状态：已由产品负责人明确确认
- 确认日期：2026-08-03
- 适用范围：V4 产品规格、架构设计、实施计划与验收
- 上游愿景：构建世界领先的新媒体运营 Agent

## Outcome

为抖音代运营团队打造能够持续经营账号、主动发现机会、完成运营行动并对结果负责的主 Agent。

系统不是等待提问的一次性聊天助手，而是持续运行的账号经营者。它能够根据用户指令和当前经营目标，动态交付账号诊断、策略、选题、脚本、拍摄任务、完整视频、发布包、人工发布任务、数据监测或运营复盘。

## User

核心用户是同时服务多个客户账号的抖音代运营团队。

运营人员从重复执行者转变为：

- 账号经营目标设定者；
- 多账号监督者；
- 高风险动作审批者；
- 异常处理与客户关系负责人。

客户侧第一阶段不直接使用完整运营 Agent。系统自动生成周报、月报、策略说明和成果，运营负责人确认后再发送给客户；客户反馈进入对应账号的长期约束和下一轮运营任务。

## Why Now

当前 V3 已具备主 Agent、Skill、专家 Agent、Tool、执行 Runtime、权限门、成果和审计等基础能力，但主要模式仍然是“用户提交一次任务，系统完成一次任务”。

下一阶段的价值不在继续增加专家或页面，而在于把这些能力连接成可持续运行、可以学习、能够产生经营结果的账号闭环。

## Operating Model

主 Agent 每天主动巡检账号并生成简洁的今日运营简报，包括：

- 异常账号；
- 增长机会；
- 待审批内容；
- 已自动完成的工作；
- 需要人工处理的风险和证据缺口。

对话仍然是主要交互入口。运营人员可以追问、修改、暂停、接管或下达新的经营目标，不需要每天从空白输入框开始工作。

## Benchmark Intelligence

系统维护每个账号独立的对标库。V4 由运营人员添加对标账号、代表作品链接、截图或其他公开材料，主 Agent 对人工选定的对象进行深度分析，提炼：

- 选题方向；
- 开头与吸引力结构；
- 内容结构和时长；
- 视觉与封面方式；
- 发布时间与节奏；
- 可验证的成功模式。

每条对标结论必须保留来源、采集时间、可见数据和证据置信度，并明确区分公开互动表现与账号后台完整数据。V4 不承诺自动持续抓取整个对标账号；未来只有在获得合规、稳定的数据来源后才增加自动监测连接器。

对标复用不是直接照搬原文、画面或品牌表达，而是结合当前账号定位和账号运营宪法重新创作，形成可以进入内容生产与发布排期的实验候选。

## Data Mainline

抖音官方 API 当前无法作为稳定的数据主链路。

现阶段正式采用“定期批量导入抖音后台导出表格”作为平台数据入口：

- 运营人员一次拖入多个不同类型的导出表格；
- 系统自动识别表格类型、账号身份、指标和时间范围；
- 相同账号、日期和业务维度的数据执行幂等合并；
- 后续导入覆盖更新重叠区间，不重复累计；
- 缺失、冲突、异常和过期数据必须显式说明；
- 未确认数据不能进入正式诊断、自动决策和复盘路径。

正式数据更新节奏为：普通账号每周完整导入一次；新发布作品在发布后第 1 天、第 3 天和第 7 天补充关键表现数据；重点活动账号可以按需要临时提高频率。主 Agent 可以每天巡检任务、权限、异常和数据新鲜度，但只有新数据导入后才能形成新的数据结论，不得把旧数据描述为实时状态。

平台数据之外，系统还应接入客服、表单、企业微信、CRM 或其他业务数据，连接内容发布、互动、咨询、有效线索和成交结果。

核心系统不得依赖脆弱、不可审计或无法稳定验证的非官方采集接口。

## Autonomous Operation Boundary

每个账号采用可升级、可降级的自治等级：

1. 只提供建议；
2. 生成执行成果并等待审批；
3. 在已批准边界内自动生成发布包、监测结果和调整建议。

V4 的抖音发布动作由运营人员手动完成。系统负责生成完整发布包、排期和人工发布任务，并在发布完成后把真实作品与原计划关联。新账号从低自治等级开始，经过真实结果和质量验证后逐步提升权限。敏感内容、重大定位变化、预算、价格政策和高风险动作始终需要人工审批。

运营者可以随时暂停自动化、修改目标、降低权限或接管账号。

## Account Constitution

每个账号拥有由客户和运营团队共同确认的“账号运营宪法”，至少包含：

- 品牌定位和目标人群；
- 经营目标和优先级；
- 内容边界与禁用表达；
- 产品、服务和价格政策；
- 发布频率与时段约束；
- 对标复用边界；
- 自动化权限和审批规则；
- 风险升级与人工接管规则。

主 Agent 可以提出修改建议，但未经批准不能自行改变长期约束。所有专家、内容生成、对标复用和自动执行都必须接受账号运营宪法校验。

## Success

系统成功不是“回答得好”或“生成数量多”，而是：

> 相比明确基线，至少一个选定目标指标产生有意义的提升，同时账号安全、品牌质量、运营成本等保护指标没有显著恶化。

一个经营周期只设置一个主目标，例如：

- 成交或有效线索；
- 粉丝净增长；
- 有效播放和互动；
- 内容生产效率；
- 人工投入时长。

其他指标作为辅助指标或保护指标。系统必须区分“高播放但不成交”和“播放一般但线索质量高”，并用真实业务结果指导下一轮运营。

## Constraints

- 第一阶段只把抖音做到极致；
- 平台数据以批量表格导入为正式主链路；
- 自动化权限必须可审计、可暂停、可降级和可接管；
- 不同客户和账号的数据、对话、记忆、成果、实验、权限及技术日志完全隔离；
- 数据不足时必须承认证据不足，不得生成伪确定结论；
- 内容和自动行动必须遵守账号运营宪法；
- 运营效果必须同时考虑业务收益、质量、安全与成本。

## Out of Scope

V4 不以以下内容为目标：

- 同时铺开多个内容平台；
- 通过浏览器自动化、RPA 或非官方接口自动发布抖音内容；
- 无边界全自动运营；
- 只用播放量定义成功；
- 用专家数量和复杂编排定义智能程度；
- 依赖当前不可用的抖音官方数据 API；
- 依赖不稳定、不可验证的非官方数据接口；
- 在证明单账号可持续经营前直接建设百账号舰队；
- 跨客户共享原始数据、对话、成果或可识别的账号记忆。

## Intent Gate

后续任何产品需求、架构设计或实现任务都应回答：

1. 它是否帮助系统形成持续经营闭环？
2. 它是否减少代运营团队的实际人力？
3. 它是否能通过真实数据验证结果？
4. 它是否遵守账号隔离、运营宪法和自动化边界？
5. 如果以上均不能证明，为什么仍应进入 V4？
